# Product Restore-on-recreate: fuzzy-matched undelete with forced mapping price-review

ADR 0009 deferred "un-soft-deleting a Product and having its previously-cascaded mappings come back" to a **Part 8.5 slice**, on the grounds that it is a *Product-layer lifecycle* concern, not a mapping-layer one, and MVP had no restore UI at all. Part 8.5 closes that carry-forward. The chosen shape is **restore-on-recreate**: there is no separate "trash" screen — instead, when a user starts creating a product and types a name (3+ chars, 400 ms debounce), a server-side **`pg_trgm` fuzzy search** over the tenant's *soft-deleted* products (`deletedAt IS NOT NULL`) surfaces likely matches, so the user re-discovers a retired record at the exact moment they would otherwise duplicate it. Eight questions were locked in a grill (Q1–Q8, Drive doc `1DlVifFHjfP6D--6h_0ZgKEIffSjfN_CILtp6uoQzFk4`): fuzzy match runs at **threshold 0.4** on `GREATEST(similarity(name), similarity(sku))`, returns the top 10 (top 5 shown + a "ดูเพิ่มอีก 5" reveal), each row carrying a coarse similarity **badge** (>0.7 ตรงกันมาก / 0.5–0.7 ใกล้เคียง / 0.4–0.5 อาจเกี่ยวข้อง — raw score never shown) and a `matched_on` tag (name vs sku) so a SKU hit with a name display does not confuse (Q1/Q2); only the **name** field triggers the typeahead — SKU is usually auto-generated, not searched-via (Q3); restore **re-uses the existing product ID** via an idempotent `UPDATE … SET deletedAt = null, updatedAt = NOW() WHERE id = $1 AND deletedAt IS NOT NULL`, so all fields revert as-is and orphan mappings recover their meaning through the unchanged FK — no new row, no field re-entry (Q4); a **SKU collision with a live product** is detected at search time (warning badge on the candidate) and resolved in the restore dialog via a `newSku` input pre-filled with `{originalSku}-restored`, validated against the partial unique index (Q5); **orphan mappings** (here meaning the mapping rows the user chose to *keep* live during the Part 8 cascade — `productId = restored, deletedAt IS NULL` — **not** the cascade-deleted ones) are left untouched by default and auto-recover when the parent flips back to live, with a read-only recoverable-mappings **preview** in the suggestion row (Q6); when orphan mappings exist the restore flow **forces a price-review step** (Q7, Option C — no threshold, accuracy over convenience for financial data), each mapping rendered as a radio (default *ใช้ราคาเดิม* / *อัปเดตราคาใหม่* revealing price/min-qty/lead-time inputs reusing the Sprint 1 zod rules); an updated mapping whose `effectiveFrom = today` is **overwritten in-place** (Option ε — a zero-duration price never used in a real transaction has no audit value), otherwise it follows the ADR 0009 supersede pattern (close old `effectiveTo`, insert a new open row) (Q7 C-sub-3); and **no dedicated audit log** is added (Q8, Option A) — `product.updatedAt`/`deletedAt`, mapping `updatedAt`, and the Part 8 history viewer already surface the state change at the data level. Bundled into the same slice is a **schema-consistency fix**: `Product.sku`'s Prisma-generated FULL `@@unique([tenantId, sku])` is replaced by a manual **PARTIAL** unique index `WHERE deleted_at IS NULL`, finally aligning Product with the `Supplier.code` (ADR 0005 era) and `SupplierProductMapping` (ADR 0009) precedent and closing the Product.sku FULL-unique soft-delete trap (Pitfall #23) — without it, a restored-or-recreated SKU would still collide with the ghost soft-deleted row (the Pitfall #22/#23 family). Chosen because restore is an *infrequent* operation where capturing intent at create-time beats a divorced admin screen, re-using the ID keeps the financial audit trail and recovers orphan mappings for free, and the partial-unique fix is a prerequisite the restore path would have hit anyway.

## Considered Options

- **(a) Restore-on-recreate — fuzzy typeahead over soft-deleted products at product-create time, re-using the existing ID (chosen)** — the user never visits a separate screen; the system catches the duplicate-creation intent in the create form itself. `pg_trgm` similarity on name+SKU (threshold 0.4, top 10) tolerates the typos and near-matches an exact-string lookup would miss ("เนื้อหมูสันใน" vs "หมูสันใน"), and re-using the ID means every field, the SKU, and the FK from kept-live orphan mappings come back intact with one idempotent UPDATE. Diverges from a "trash bin" model **by design**: SME users do not think in terms of administering deleted rows, they think "I'm adding pork again" — so the affordance lives where the intent is. The cost is a debounced server endpoint + two GIN indexes, paid once.
- **(b) Exact-SKU-collision restore only — no fuzzy search, detect a re-create solely when the typed SKU matches a soft-deleted row (rejected)** — far cheaper (no `pg_trgm`, no indexes), but defeated by Q3's own premise: SKU is **auto-generated** (`P-####`), so the user rarely types it and a fresh create would mint a *new* SKU that never collides with the old soft-deleted one. The restore would almost never trigger, leaving the carry-forward effectively unclosed.
- **(c) Separate trash / restore admin page — list soft-deleted products with a "กู้คืน" button (rejected)** — conceptually clean and discoverable from a settings menu, but divorced from the moment of intent: the user who is about to duplicate a product is on the *create* form, not browsing a trash list, so duplicates still get made and only cleaned up later (if ever). Kept as a forward-compatible escalation — the same `restoreProductLogic` + fuzzy-search logic could back such a page later without data migration.
- **(d) No restore — manual re-create, status quo (rejected)** — leave Part 8.5 unbuilt; the user re-creates the product from scratch and loses the kept-live orphan mappings' meaning (they stay attached to a permanently dead parent). Rejected because ADR 0009 explicitly recorded this as a deferred slice to *build*, the orphan-mapping recovery has real SME value, and the prerequisite SKU partial-unique fix (Pitfall #25) needs doing regardless.

## Consequences

- **One Part 8.5 L1 schema pass covers the `pg_trgm` enablement + indexes + the SKU unique fix.** `CREATE EXTENSION IF NOT EXISTS pg_trgm` (verified runnable on this Neon project before L1 — no permission block, fallback to `ILIKE` not needed), two **partial GIN** indexes `products_name_trgm_idx` / `products_sku_trgm_idx` `USING gin (… gin_trgm_ops) WHERE deleted_at IS NOT NULL` (the index covers only the soft-deleted target set — smaller, faster), and the unique-index swap. The `@@unique([tenantId, sku])` is **removed from `schema.prisma`** (replaced by a `///`-comment pointing at the manual file, mirroring `Supplier.code`), and `prisma/manual/product_sku_unique.sql` ships `DROP INDEX IF EXISTS product_tenant_id_sku_key; CREATE UNIQUE INDEX product_tenant_id_sku_unique ON product (tenant_id, sku) WHERE deleted_at IS NULL;`. Greenfield (production has no rows) so every edit is non-destructive.
- **Pitfall #23 (Product.sku FULL `@@unique` soft-delete trap) is closed as a bonus.** With the full unique gone, a soft-deleted row's SKU no longer blocks a re-create or a restore-with-same-SKU; the surviving collision case (two *live* rows) is exactly what the partial index still catches, mapped to `ProductSkuConflictError` → Thai on P2002 (unchanged Sprint 1 behaviour). **Pitfall #25 (`generateSku` concurrent-scan race) is NOT addressed here** — it still needs an advisory lock / DB sequence per tenant at scale (deferred); both candidate rows are live, so partial-vs-full unique does not change the race outcome.
- **Restore is a single idempotent UPDATE; orphan-mapping recovery is implicit, not a separate write.** `restoreProductLogic(tenantId, productId, { newSku?, mappingUpdates? })` flips `deletedAt → null` (guarded by `deletedAt IS NOT NULL`, so a double-submit is a no-op) and, only if `newSku` is supplied, rewrites the SKU in the same statement. Kept-live orphan mappings (`deletedAt IS NULL`) regain meaning automatically because their FK never changed; cascade-soft-deleted mappings stay deleted (respecting the user's earlier Part 8 Q6 hybrid choice) — reviving those is deferred to manual re-creation.
- **The restore dialog has 0–2 conditional sections** (Risk #3): SKU conflict (Q5) and/or orphan-mapping price review (Q7); with neither, restore is a single confirm. The price-review step is **mandatory whenever orphan mappings exist** (Option C, no threshold) — each row defaults to *ใช้ราคาเดิม* (conservative; an explicit radio flip is required to supersede), and updated fields (`currentUnitPrice` > 0, `minOrderQty` > 0, `leadTimeDays` 0–365) reuse the Sprint 1 mapping zod; `effectiveFrom`, supplier item code/name, and `isPreferred` are kept as-is.
- **Same-day price updates overwrite in place; older ones supersede** (Option ε, Q7 C-sub-3). When an updated orphan mapping's `effectiveFrom = today` (Bangkok UTC+7 — Risk #4 requires consistent date handling, see Decision #60), the row is `UPDATE`d directly rather than closed-and-reinserted, because a zero-duration price row that never backed a real transaction has no audit value. Otherwise the ADR 0009 atomic supersede applies (close old `effectiveTo = today`, insert a new open row). This keeps the Part 8 schema/ADR untouched and resolves the same-day double-restore edge (E1) without a unique-constraint violation. **Tech-debt note:** Sprint 1's mapping *edit* flow currently throws `MappingOverlapError` on a same-day supersede; whether this in-place pattern should generalise there is flagged for Sprint 2/3, not decided here.
- **No new audit surface** (Q8, Option A): WHO/HOW-MANY-TIMES/WHY a restore happened is not tracked — consistent with Sprint 1 (which has no audit pattern to extend) and acceptable for a 1–2-user-per-tenant SME MVP. The history viewer surfacing restore-time price changes is the business-level audit. If audit ever becomes critical, a generic `audit_log` retrofitting all entities at once in a dedicated sprint is preferred over piecemeal columns.
- **All 108 Sprint 1 logic tests must remain green after the unique-index swap** (Risk #2) — verified immediately after the L1 migration and again at L6. The manual-partial-index approach is the proven `Supplier.code` / `SupplierProductMapping` pattern, so the risk is the migration mechanics, not the design.
