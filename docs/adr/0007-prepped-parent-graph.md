# PREPPED products form a parent graph guarded at write-time, not in the schema

A `Product` with `type="PREPPED"` points to a `parentProductId` that may be either a RAW **or** another PREPPED (honoring Decision #58's depth-5 chain). The schema permits any self-relation, so the correctness rules live in app logic — `*Logic` functions reject cross-tenant parents, self-references, cycles, and any edge that would push the longest live chain through this node past depth 5. The check is run on every create and update inside the same transaction as the write, BEFORE the row is persisted, so the DB never holds a forbidden structure (modulo the documented concurrent-write race — Pitfall #28). Delete of a product that still has live children is blocked outright; soft-deleted children don't count. PREPPED requires `parentProductId` + `yieldPercent`; RAW forces both to null. Yield is product-specific (Decision #59 math); `expectedYieldG` is deferred out of 7c because it needs a batch-size concept (Sprint 2-3). Chosen because PREPPED chains are how a kitchen actually models work (whole salmon → portioned fillets → seasoned fillets), and any simpler rule either rejects legitimate kitchen graphs (forbid PREPPED-from-PREPPED) or quietly admits broken ones (upward-only depth check, cascade-on-delete).

## Considered Options

- **Full live-only ancestor + descendant check at write-time (chosen)** — on setting `X.parent = P`, require `ancestorDepth(P→root) + 1 + descendantHeight(X) ≤ 5`, with both walks restricted to `deletedAt:null` nodes and a visited-set guard (so an already-cyclic DB doesn't loop). Self-ref (`P=X`) and cycle (X encountered on the upward walk) reject. On **create**, X has no children → `descendantHeight=0` → it reduces to the cheap `ancestorDepth(P)+1 ≤ 5` check; the descendant-DFS is only paid on edit. Catches every kitchen graph anyone would actually build, and never lets one through that breaks Sprint 5's recipe-cost recursion limit (Decision #58).
- **Upward-only depth check** — measure `ancestorDepth(P)+1` only, never look at X's subtree. Cheaper on edit. Rejected: re-parenting a node that already has a deep subtree below it can produce a chain >5 the recipe engine will refuse to cost — and we'd only find out at cost-compute time, far from where the bad edit happened. Concrete trace: `X` already has `C→B→A→leaf` below it (descendantHeight = 3). Move `X` under `P` where `ancestorDepth(P) = 3`. The new longest chain through `X` is `P-root … P → X → C → B → A → leaf` = 7 deep. Upward-only sees `3 + 1 = 4 ≤ 5` ✅ and wrongly passes; the full check sees `3 + 1 + 3 = 7 > 5` ✗ and rejects. The whole point of write-time enforcement (Q2 in the grill) is to catch this here.
- **Cascade-delete (delete a parent, soft-delete its children too)** — silent mass delete of a tree the user may not have meant to touch. Rejected: invisible blast radius.
- **Detach-on-delete (null the child's `parentProductId`)** — leaves PREPPED children dangling without a parent, which contradicts Q2's "PREPPED must have a parent" invariant. Rejected.
- **Block-delete-with-live-children (chosen for delete)** — pre-check `count(children where parentProductId=id AND deletedAt:null) > 0` → throw `ProductHasChildrenError` (action maps to Thai, lists the blocking child names, truncates "…และอีก N รายการ"). Forces the user to deal with the subtree explicitly. Also closes the "live-child → soft-deleted-parent" dangling case for free: a live child always has a live parent, so `assertRefBelongsToTenant(parentId)` on a re-validating update never fails (Q7).

## Consequences

- **`parentProductId` has no `@@unique`, no DB-level cycle/depth constraint.** A future reader who searches the schema for "how PREPPED depth is enforced" will find nothing — the answer is `assertParentValid` in `src/server/product.ts`, called from create + update. Same pattern as ADR 0006's per-row dimension rule.
- **The longest live chain is what counts, not the column type.** Soft-deleted nodes are skipped in both the upward walk and the descendant DFS. This means restoring a soft-deleted product (not in MVP) would need to re-run depth validation, since restore can suddenly extend a previously-shortened chain. Out of scope for 7c; document when restore lands.
- **Type-change is allowed on edit.** RAW→PREPPED reveals + requires `parentProductId` and `yieldPercent`; PREPPED→RAW the server forces both to null. Safe in Sprint 1 because no downstream feature references `Product.type` yet. **Deferred guard:** Sprint 2+, once procurement/recipe/stock touch `type`, add a write-time guard on changing it — same family as ADR 0005's base-unit-change guard and ADR 0006's deferred multi-unit-referenced-by-mapping guard. Recorded in CONTEXT.md so it isn't lost.
- **`sku` stays `P-####` for both types** (`generateSku` unchanged). A `PP-` prefix for PREPPED was considered and rejected: type-change would break the convention, and Part 8's `SupplierProductMapping` needs sku stability across edits.
- **Concurrent-edit race accepted for MVP** (Pitfall #28): two transactions each editing different nodes on the same chain can both pass the read-then-write check and produce a cycle the DB now holds. At scale, fix with `pg_advisory_xact_lock` keyed off `tenantId` (family of Pitfall #25). The visited-set guard in the walker means even if the race lands, the depth check on the NEXT write still terminates instead of looping.
- **`expectedYieldG` column stays nullable and out of the 7c form.** A future reader who sees the column should not infer it's wired up — it isn't, by design, until batch sizing exists.
