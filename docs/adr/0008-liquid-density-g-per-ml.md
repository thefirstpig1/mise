# Liquid density is stored as g/ml on a global non-deletable template, XOR'd with a per-product override

A `Product` carries either a foreign key to a `LiquidDensityTemplate` (global, system-seeded — น้ำเปล่า, นมสด, …) **or** a per-product numeric `densityGPerMlOverride`, **never both** (enforced at zod, at the action-layer cleanse, and by a Postgres CHECK constraint). The unit is **g/ml** (standard density): water = 1.000, milk = 1.030, cooking oil = 0.910. The column was originally named `ml_per_g` (Pitfall #27) — its seed values were always g/ml-direction density that anyone could cross-check against Google ("ความหนาแน่นนม" returns 1.03 g/ml), but the column name said the opposite. Part 7d renames `ml_per_g → g_per_ml` (and `density_ml_per_g_override → density_g_per_ml_override`) so name matches reality. Templates have no `deletedAt`, no tenant scope, no `isActive` — they are an app-level constant table managed via seed (now `upsert by name`, requiring `name @unique` — Pitfall #22/#23 family does NOT apply here because the table has no soft-delete). Density is **data-capture only** in Part 7d: there is no resolver, no WEIGHT↔VOLUME conversion, no cost-engine consumer; that all lives in Sprint 2+ and reads `template?.gPerMl ?? override` as a single path. Chosen because g/ml is the unit a kitchen and a chemistry textbook both recognise, the existing seed values were already correct in that direction, and bundling the rename + XOR CHECK + name-unique into one migration before any UI consumes the column avoids ever having to migrate live density data later.

## Considered Options

- **(a) Rename column `ml_per_g → g_per_ml`, keep seed values (chosen)** — values were already standard g/ml density, name was wrong; one `ALTER TABLE ... RENAME COLUMN` per affected table (`liquid_density_template`, `product`) flips the lie cheaply since no UI or downstream code reads the column yet. Pairs with Q2's XOR rule and Q8's `name @unique` in a single migration `part_7d_density_data_capture`. Future cost-engine math is the unsurprising direction (`weight = volume × density`, not `weight = volume / specificVolume`), so call sites never invert.
- **(b) Keep `ml_per_g`, flip seed values (rejected)** — would have re-written the values to true specific-volume (milk 1.030 → 0.971, oil 0.910 → 1.099, syrup 1.300 → 0.769). Cheap migration but every value diverges from the worldly standard a user can Google: a tenant reading "นมสด 0.971" in the picker has no way to verify, and a future cost engine must invert at every call. Reverses the chemistry to match a name, instead of fixing the name to match correct values.
- **(c) Override-wins precedence with template as label-hint (rejected for Sprint 1)** — would let a product set BOTH `liquidDensityTemplateId` (categorisation) and `densityGPerMlOverride` (the value actually used), resolving to `override ?? template.gPerMl`. Has a real use case (an in-house syrup branded as "น้ำเชื่อม" but measured at 1.15 g/ml). Rejected for MVP because Sprint 1 has no consumer of the value yet, so the precedence rule earns no benefit while adding two-state ambiguity; XOR keeps the mental model "either standard OR custom, never both" and is **forward-relaxable** — going XOR → override-wins is non-breaking (existing rows remain valid), while the reverse would require migrating any "both set" rows. Pitfall #28's family ("read-then-write race") doesn't apply here, but the same general principle does: tighten now, relax later when there's a concrete need.
- **(d) Cascade soft-delete / lifecycle on `LiquidDensityTemplate` (rejected for MVP)** — adding `deletedAt` (or `isActive`) would let admins retire a template without removing the row. Rejected because the table is global (no tenant scope), seed-managed, ~5 rows, and never user-edited; lifecycle complexity here would solve no current problem. If it ever IS added, the migration must swap the FULL `name @unique` for a partial index `WHERE deleted_at IS NULL` (precedent: `prisma/manual/supplier_code_unique.sql`) to avoid re-treading Pitfall #22/#23 — recorded as a comment on the `@unique` line in `schema.prisma` so the next reader spots it without history-spelunking.

## Consequences

- **One Part 7d migration covers three schema edits** (`part_7d_density_data_capture`): RENAME COLUMN ×2 (Q1), `CREATE UNIQUE INDEX liquid_density_template_name_key` (Q8), and `ALTER TABLE product ADD CONSTRAINT product_density_xor CHECK (liquid_density_template_id IS NULL OR density_g_per_ml_override IS NULL)` (Q2). The migration is preceded by two read-only sanity checks (duplicate names; existing rows with both FK and override set) — if either returns rows, the migration is halted and the data is fixed, never the constraint loosened.
- **XOR is enforced at three layers** (defense in depth): zod `.superRefine` rejects "both set" client-side; `rawFromFormData` cleanses the inactive mode's field to `null` on the server so a stale form value cannot survive a mode toggle; the DB CHECK is the final backstop for any raw-SQL or direct-Prisma write that bypasses the action layer. A bug at any one layer is caught by the next.
- **Density is gated to `primaryDimension !== "COUNT"`** at zod, in the UI (whole section hides when COUNT), and in the server cleanse (which runs BEFORE zod so a VOLUME → COUNT toggle that leaves density values in the form does not produce a validation error — mirrors 7c's PREPPED → RAW cleanse ordering). COUNT-primary products cannot carry density even via raw write paths that pass zod (the action-layer cleanse still applies); a DB-level constraint is not added because `primaryDimension` is a free-form string column to Postgres and the cross-column check would be fragile.
- **Sprint 2+ density resolver is a single line: `template?.gPerMl ?? override`.** Because of XOR, exactly one operand is non-null when density exists; the resolver does not have to decide precedence, log conflicts, or pick a tie-breaker. This is the load-bearing benefit of choosing XOR over option (c) — every consumer site reads density the same way with no branching.
- **`name @unique` on `LiquidDensityTemplate` is FULL, not partial** — safe because the table has no `deletedAt`. The schema comment above the `@unique` line names the precedent (`supplier_code_unique.sql`) and the conditions under which a future maintainer must swap to partial: "if `deletedAt` is ever added, replace this with a partial index." Without that comment, Part 7d's safe FULL unique would silently become Pitfall #22/#23 the moment lifecycle is added; with it, the trap is visible at the line that would have to change.
- **Seed pattern changes from `findFirst + create-if-absent` to `upsert by name`** (enabled by the new unique). Re-running `pnpm prisma db seed` now propagates any value edit in `LIQUID_DENSITIES` (e.g., a future calibration: milk 1.030 → 1.032) to the existing row, and via FK to every linked product on next read. Two clarifying comments are added to `seed-system.ts`: the update procedure for admins, and the note that "rename a template name" is a breaking change that orphans every FK pointing to the old row.
- **CONTEXT.md becomes the canonical wording for "Liquid density"** in g/ml direction, with the XOR rule, the COUNT gate, and the global non-deletable nature explicit. Pitfall #27 is marked `resolved-in-7d` with a one-line pointer back to this ADR; the original wrong-direction wording is left intact in Pitfall history (it's the bug story, not the current state).
- **No expanded scope into Sprint 2 concerns.** Density inheritance (PREPPED reading parent's density when not set) and ADR 0005 base-unit-change interactions with density are explicitly out of Part 7d and recorded as deferred guards in sprint-progress; this ADR does NOT pre-commit either decision.
