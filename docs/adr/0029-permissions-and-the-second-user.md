# ADR 0029 — สิทธิ์: capability ที่คอมไพเลอร์บังคับ และคนที่สองที่ยังไม่เคยมี

**Status:** accepted · **Date:** 2026-08-30 · **Grill:** Q1–Q16
**Parts:** Sprint 6 Part 28 (สิทธิ์) + Part 29 (เชิญคนเข้าร้าน) — ADR ฉบับเดียวคุมทั้งสอง (Q16)
**Pays** ADR 0021 Q18 ที่ค้างมา 6 Parts · **ล้ม** master-spec §H.4 ทั้งหมด (Q4, Q5, Q8, Q9) · **ไม่แตะ** RLS ที่ ADR 0004 เลื่อนไป Sprint 7

## Context

ประโยคที่ส่งต่อกันมาตั้งแต่ ADR 0021 Q18 คือ *"any authenticated member of a tenant can perform any action, including a `viewer`"* — grill รอบนี้เริ่มจากการอ่านโค้ดก่อนเชื่อประโยคนั้น และพบว่ามันจริงครึ่งเดียว ในทางที่เปลี่ยนรูปคำถามทั้งหมด

แปดข้อที่ยืนยันจากการอ่านโค้ดระหว่าง grill

1. **`canPerform` (`permissions/service.ts:107`) ไม่มี call site เลย และเพื่อนของมันก็เหมือนกัน** — `canAccessBranch:130`, `canAccessDepartment:139`, `getUserContext` ทั้งสี่ตัวมี 0 call site นอกไฟล์ตัวเอง `PermissionService` มีมาตั้งแต่ Sprint 0 และไม่เคยถูกเรียกเลยแม้แต่ครั้งเดียว

2. **`tenant-init.ts:50` เป็นที่เดียวในโปรเจกต์ที่เขียน `tenant_membership` และมันเขียน `role: "owner"` แบบ hardcode** ไม่มีหน้าเชิญคน ไม่มีหน้าแก้ role ไม่มี raw SQL ไหนแตะตารางนี้ **ทุก tenant จึงมีสมาชิกคนเดียว และเป็น `owner` เสมอ** — `viewer`, `kitchen_staff`, `purchaser`, `accountant`, `manager` เป็น string ในคอมเมนต์ที่ยังไม่เคยมีตัวตน ช่องโหว่ที่ค้างมา 6 Parts จึง **จริงในเชิงโค้ด แต่ยังไม่มีวันที่เกิดขึ้นได้จริง**

3. **`ROLE_PERMISSIONS` (`service.ts:86`) บรรยายระบบที่ไม่เคยถูกสร้าง** — `purchase_request` และ `sales_transaction` ไม่มีตารางในฐานข้อมูล (Part 11 กลืน Part 12, และ Sprint 4 สร้าง `sales_day`/`sales_line` แทน) ขณะที่ `waste_log`, `par_level`, `stock_transfer`, `stock_adjustment`, `stock_cost_declaration`, `menu_alias`, `menu_merge`, `sales_import_profile`, `sales_day`, `sales_line`, `sales_consumption_run`, `staff_member`, `staff_meal`, `recipe_branch` ไม่มีที่ยืนในเมทริกซ์ **2 ใน 15 ชื่อชี้ไปที่ตารางที่ไม่มีอยู่ และตารางจริงราว 14 ตัวหายไป** เราไม่ได้กำลังต่อสายของเดิม เรากำลังเขียนกฎขึ้นใหม่ทั้งชุด

4. **`requireTenant()` คือคอขวดเดียวที่ทั้งการอ่านและการเขียนต้องผ่าน** — ถูกเรียก **145 ครั้งใน 79 ไฟล์** โดย 70 ครั้งอยู่ในไฟล์ `actions.ts` สถาปัตยกรรมแยกชั้นไว้สะอาดอยู่แล้ว: `src/server/*.ts` เป็นตรรกะล้วนที่รับ `tenantId` เป็นพารามิเตอร์และไม่รู้จัก session ส่วน `"use server"` ทั้งหมดอยู่ใน `src/app/**` และเรียก `requireTenant()` ก่อนเสมอ

5. **`/signup` เป็นหน้าที่ไม่ต้อง login และมันทำ `prisma.user.upsert({ where: { email } })` อยู่แล้ว** — เครื่องมือ "ผูกอีเมลเข้ากับ tenant" มีอยู่และถูกใช้งานจริงทุกวัน ขณะที่ `auth.ts` เป็น Auth.js magic link ล้วน ไม่มีรหัสผ่าน และ production email ยัง `throw new Error("Production email not configured yet (Sprint 7)")`

6. **`require-tenant.ts:38` เลือก membership เก่าสุดเงียบ ๆ** (`orderBy: { createdAt: "asc" }`) วันนี้ไม่มีใครเดือดร้อนเพราะไม่มีใครมี 2 membership ได้ — ทันทีที่คนที่สองมีอยู่จริง มันจะกลายเป็นการเดาที่ไม่บอกใคร

7. **`user_branch_access` ถูกเขียนตั้งแต่ `tenant-init.ts:66` มาตลอด โดยไม่มีใครอ่าน** ส่วน `departmentId` ปรากฏบนตารางธุรกิจเพียง 3 ตาราง (`po_item_allocation`, `gr_item_allocation`, `expense_item`) ขณะที่ `branchId` ปรากฏ 58 ครั้งใน schema · `enableDepartments` default `false` · และ ADR 0022 Q8 ปฏิเสธการใส่ department ลง ledger ไปแล้ว

8. **`own_record` ของ H.4 คำนวณไม่ได้บนเอกสารที่มันสำคัญที่สุด** — `stock_count`, `goods_receipt`, `sales_consumption_run` ไม่มีคอลัมน์บอกผู้ทำเลยสักตัว ส่วน `waste_log`, `stock_transfer`, `staff_meal` บันทึกเป็น **ข้อความอิสระ** (`wasted_by_name`, `dispatched_by_name`, `recorded_by_name`) ซึ่ง ADR 0028 Q4 เพิ่งจงใจกันไม่ให้ `staff_member` เข้าไปแทนที่เมื่อสองวันก่อน

## Decision

### Q1 — ด่านกับคนที่จะถูกกั้น เป็นการออกแบบชิ้นเดียวกัน

ถ้าต่อสาย `canPerform` วันนี้โดยไม่มีทางสร้างคนที่ไม่ใช่ `owner` ผลลัพธ์คือด่าน 145 จุดที่ทุก request ตอบ `true` เสมอ — ด่านที่ยังไม่เคยมีใครเดินผ่าน และไม่มีผู้ใช้จริงคนไหนถูกปฏิเสธ ADR 0021 Q18 ปฏิเสธของแบบนี้ไปแล้วด้วยเหตุผลที่ยังใช้ได้อยู่: *ระบบที่ดูเหมือนถูกป้องกันแต่ไม่ได้ถูกป้องกัน แย่กว่าระบบที่เปิดโล่งอย่างเปิดเผย เพราะคนจะเลิกระวัง*

การเชิญคน การมอบ role และการบังคับสิทธิ์ จึงถูกออกแบบพร้อมกันใน ADR ฉบับเดียว (การ**ลงมือ**แยกเป็นสอง Part — Q16)

*(ปฏิเสธ: **เลื่อนทั้งหมดออกไป** เพราะยังไม่มีใครสร้าง `viewer` ได้ — Beta ที่มีร้านจริงต้องมีคนที่สองแน่นอน เจ้าของไม่นับสต๊อกเอง)*

### Q2 — คำเชิญ *คือ* แถว `tenant_membership` ไม่ใช่ตารางใหม่

owner กรอกอีเมล → `user.upsert` + สร้าง `tenant_membership` พร้อม role ทันที · ผู้รับไปที่ `/login` พิมพ์อีเมลตัวเอง รับ magic link ตามปกติ · `requireTenant` เจอ membership แล้วเข้าได้เลย ไม่มีขั้นตอน "ยอมรับคำเชิญ" แยก เพราะ **magic link คือการพิสูจน์ความเป็นเจ้าของอีเมล ซึ่งเป็นการยอมรับอยู่ในตัวแล้ว**

- ยกเลิกคำเชิญ / ถอดคนออก = `isActive = false` (คอลัมน์มีอยู่ และ `require-tenant.ts:36` กรองอยู่แล้ว)
- "ยังไม่เคยเข้าใช้" อ่านจาก `user.emailVerified === null` — ไม่ต้องมีคอลัมน์สถานะ
- ไม่มี migration และไม่มีอีเมลใบใหม่

*(ปฏิเสธ: **ตาราง `tenant_invitation` + token.** มันประดิษฐ์ credential ใบที่สองขึ้นมาทำสิ่งที่ magic link ทำอยู่แล้ว — ต้องดูแล หมดอายุ เพิกถอน — และ credential ใบนั้นส่งไม่ได้จนถึง Sprint 7 (Context 5) เท่ากับผูกความสำเร็จของ Part นี้ไว้กับ blocker เดียวกับ Part 20b)*

### Q3 — `requireTenant` ห้ามเดาว่าเป็นร้านไหน

พอ Q2 ทำให้คนหนึ่งคนมีหลาย membership ได้ `require-tenant.ts:38` จะกลายเป็นการเดาที่เงียบ (Context 6) — บัญชีนอกที่ดูแล 3 ร้าน หรือคนที่เคยสมัคร Mise ให้ร้านตัวเองแล้วถูกเชิญเข้าร้านเพื่อน จะเห็นแต่ร้านเดียวตลอดไปโดยไม่มีอะไรบนจอบอก

**มี active membership > 1 → redirect ไปหน้า "เลือกร้าน" ที่เขียน tenantId ลง cookie** คนที่มี membership เดียวไม่เคยเห็นหน้านี้เลย `requireTenant` redirect อยู่แล้วสองทาง (`/login`, `/signup`) ทางที่สามไม่ใช่รูปแบบใหม่

🔴 **cookie ไม่ใช่ของที่เชื่อได้** `requireTenant` ต้องอ่าน membership ทั้งหมดก่อนเสมอ แล้วใช้ cookie **เลือกจากในลิสต์นั้น** เท่านั้น — ห้ามใช้ค่าจาก cookie ไปสร้าง query โดยตรงเด็ดขาด ถ้าเชื่อ cookie ตรง ๆ มันคือช่องข้าม tenant ที่ร้ายกว่าทุกอย่างที่ ADR ฉบับนี้กำลังจะปิด

*(ปฏิเสธ: **ห้ามมี membership ที่สอง** — ปิดประตูใส่บัญชีนอกซึ่งเป็นรูปแบบที่มีจริงมากในร้าน SME ไทย และเป็นการปฏิเสธที่ไม่ใช่ *inability* ปฏิเสธ: **header ร่วม + ตัวสลับร้าน** — `src/app/layout.tsx` render `{children}` เปล่า ๆ และ `src/components/layout/` ว่างเปล่าไม่มีใคร import แปลว่าโปรเจกต์นี้ยังไม่มี shared chrome เลย การสร้างมันจะกลืน Part นี้ทั้ง Part ด้วยงาน UI ที่ไม่เกี่ยวกับสิทธิ์ · หน้าเลือกร้านยกระดับเป็นตัวสลับได้ฟรีในวันที่มี header เพราะเขียน cookie ตัวเดียวกัน)*

### Q4 — หน่วยของสิทธิ์คือ capability ที่มีชื่อ ไม่ใช่ `resource × action`

`ResourceType` / `Action` / `ROLE_PERMISSIONS` **ถูกลบทิ้ง ไม่ใช่แก้** แทนที่ด้วยรายการ capability แบน ๆ ที่แต่ละ surface ประกาศเพียงตัวเดียว

เหตุผลที่ชี้ขาดไม่ใช่ความสวย แต่คือ **`resource × action` บังคับให้ทุกอย่างต้องเป็น "ของ" ก่อนถึงจะป้องกันได้ และของที่ต้องป้องกันจริงในระบบนี้หลายอย่างไม่ใช่ของ** — **ต้นทุน** ไม่ใช่ตาราง (ADR 0014: cost is stored nowhere มันคือผลลัพธ์ของการ replay) · **การอนุมัติ PO** ไม่ใช่ตาราง · **การเชิญคน** ไม่ใช่ตาราง เมทริกซ์ที่มีแกนเป็น `ResourceType` จะบังคับให้เราประดิษฐ์ resource ปลอมชื่อ `"cost"` ขึ้นมาเพื่อให้เช็คได้ ซึ่งเป็นการโกหกในโครงสร้างข้อมูล

และมันละลายข้อบกพร่องที่ ADR 0021 Q18 ตั้งชื่อไว้: *"`kitchen_staff` ไม่มีสิทธิ์ `recipe` เลย ทั้งที่คนครัวคือคนที่ต้องอ่านสูตรมากที่สุด สิ่งที่เขาไม่ควรเห็นคือต้นทุน เมทริกซ์มีแกนเดียวและบอกความต่างนี้ไม่ได้"* — `cost:view` เป็น capability เท่าเทียมกับตัวอื่น ไม่ต้องมีแกนที่สาม

### Q5 — บังคับสองแกน: role + branch · department ไม่อยู่ใน Part นี้

คนที่สองที่ร้านจะเชิญเป็นคนแรกแทบแน่นอนว่าคือ **ผู้จัดการสาขา** และ role อย่างเดียวช่วยไม่ได้เลย เพราะ `manager` *ต้อง* เขียนได้ สิ่งที่ต้องแคบคือ **สาขาไหน**

- **เขียน:** `canAccessBranch` ที่ทุก action ที่รู้ `branchId`
- **อ่าน:** ไม่ไล่ปะทีละหน้า แต่**บีบที่ต้นทาง** — *รายชื่อสาขาที่คุณเห็น = รายชื่อสาขาที่คุณมีสิทธิ์* ที่ `branch.findMany` ทั้ง **9 จุด** ทำให้ทั้ง dropdown เลือกสาขา และ loop "ทุกสาขา" ใน `/cost` แคบลงพร้อมกันด้วยกฎเดียว

**department ไม่ถูกต่อสาย** — มันแยกได้แค่ 3 ตาราง ledger ไม่มีมันตามมติ ADR 0022 Q8 และ default คือปิด (Context 7) ถ้าต่อสายตอนนี้จะได้ด่านที่เกือบทุก tenant เดินผ่านแบบ `enableDepartments === false → return true` เสมอ ซึ่งคือด่านเขียวตลอดที่ Q1 เพิ่งปฏิเสธ `canAccessDepartment` **ไม่ถูกลบ แต่ต้องมีคอมเมนต์บนตัวมันบอกว่าทำไมถึงยังไม่ถูกเรียก** ไม่งั้นอีก 6 Parts จะมีคนเจอมันแล้วถามคำถามเดิม

### Q5b — "ทุกสาขา" เป็นคุณสมบัติของ *การเข้าถึง* ไม่ใช่ของ *role*

ผู้จัดการเขตที่ดูแลทุกสาขาไม่มีที่ยืนในแบบจำลองเดิม: จะให้เป็น `owner` ก็ได้สิทธิ์บิลลิ่งกับลบร้านไปด้วย จะ enumerate ทุกสาขาก็หายไปจากสาขาที่ 6 เงียบ ๆ ในวันที่ร้านเปิดเพิ่ม

**`tenant_membership.all_branches Boolean @default(false)`** และ **ลบ owner bypass ที่ `service.ts:131` ทิ้ง** — ตั้ง `all_branches = true` ให้ owner ที่ `tenant-init.ts` แล้วการตรวจสาขาเหลือบรรทัดเดียวที่ไม่มีคำว่า role อยู่ในนั้นเลย:

```ts
return user.allBranches || user.allowedBranchIds.includes(branchId);
```

เหตุผลหลักไม่ใช่ตัวฟีเจอร์ แต่คือ **Q4 ให้ role ตอบว่า "ทำอะไรได้"** ถ้า reach ยังถูกตอบด้วย role อยู่ เราก็ยังมีสองความหมายปนกันในคอลัมน์เดียว และคำถามแบบ "ผู้จัดการเขต" จะเด้งกลับมาเรื่อย ๆ — ผู้จัดการเขต, บัญชีที่ดูทุกสาขาแต่แก้อะไรไม่ได้, เจ้าของที่ดูแค่สาขาเดียว ทั้งสามเป็นการติ๊กช่องเดียว ไม่ใช่ role ใหม่สามอัน

*(ปฏิเสธ: **role `area_manager`** — เอา "ทำอะไรได้" ผูกกับ "ที่ไหน" แล้ว role จะเพิ่มแบบคูณ ไม่ใช่แบบบวก: `area_purchaser`, `area_accountant`, …)*

### Q6 — capability เป็นพารามิเตอร์ **บังคับ** ของ `requireTenant`

```ts
const { tenantId, membership } = await requireTenant("stock:write");
```

โหมดพังที่แท้จริงของงานนี้ไม่ใช่กฎผิด แต่คือ **Part ถัดไปเพิ่ม action ใหม่แล้วไม่มีใครใส่ด่านให้** แล้วไม่มีอะไรร้อง การทำให้พารามิเตอร์บังคับแปลว่า `pnpm tsc` **แดงทันทีที่มีหน้าหรือ action ใหม่ที่ไม่ยอมบอกว่าตัวเองต้องการสิทธิ์อะไร — ลืมไม่ได้เพราะมันไม่คอมไพล์** และ "ใครทำสิ่งนี้ได้" ตอบด้วย `grep` ได้ เพราะ capability อยู่บรรทัดแรกของทุก surface

โปรเจกต์นี้มีรสนิยมนี้อยู่แล้วและมันได้ผลมาแล้ว — enum drift guard ใน `stock-movement.ts` ยิงตั้งแต่ `tsc` ครั้งแรกของ Part 26 ตรงตามที่ Part 13 สร้างมันมาเพื่อการนี้ **ด่านที่ดีที่สุดในโค้ดเบสนี้คือด่านที่แดงตอนคอมไพล์**

surface ที่ไม่มี capability ที่สมเหตุสมผล (`/dashboard`, `/settings`, หน้าเลือกร้านของ Q3) ต้องส่งค่าที่พูดออกมาตรง ๆ ว่า *แค่เป็นสมาชิกก็พอ* — เขียนไว้ชัดดีกว่าเว้นว่างแล้วให้คนเดา

*(ปฏิเสธ: **`requireCapability()` แยกตัว + เทสต์ coverage** — ด่านกลายเป็นการเรียกฟังก์ชันที่ลืมได้ เทสต์จับได้ตอนรัน ไม่ใช่ตอนคอมไพล์ และหน้าใหม่ที่ไม่มี layout ครอบจะหลุดเงียบ)*

### Q7 — เขียนต้องขอสิทธิ์ · อ่านเปิด ยกเว้นรายการลับที่ระบุชื่อ

**capability เขียน (13):** `master:write` · `purchase:write` · `purchase:approve` · `receive:write` · `stock:write` · `count:write` · `expense:write` · `sales:import` · `consumption:post` · `recipe:write` · `staffmeal:write` · `member:manage` · `settings:write`

**capability อ่าน — เฉพาะที่ลับจริง (4):** `cost:view` (ต้นทุน ราคาซื้อ food cost % กำไรขั้นต้น) · `expense:view` (ค่าเช่า ค่าน้ำค่าไฟ) · `sales:view` (ยอดขาย) · `staff:view` (ใครกินอะไร — PDPA)

ที่เหลืออ่านได้หมด: สต๊อกคงเหลือ สินค้า **ตัวสูตร (ไม่ใช่ต้นทุนของสูตร)** par level

เหตุผลที่ไม่ทำ `:view`/`:write` ครบทุกกลุ่ม: `stock:view`, `product:view`, `recipe:view` จะถูกให้ทุก role อยู่ดี เพราะไม่มีใครอยากห้ามคนครัวดูของในสต๊อก **สวิตช์ที่เปิดตลอดคือด่านเขียวตลอด** และมันจะทำลายสิ่งที่ Q6 ซื้อมาด้วย — การตัดสินใจที่ 145 จุดจะกลายเป็นการประทับตรา แต่ภายใต้ Q7 คำถามที่ทุกจุดต้องตอบคือ **"หน้านี้แสดงเงินที่ไม่ใช่ทุกคนควรเห็นหรือเปล่า"** ซึ่งเป็นคำถามจริง ตอบผิดได้ และตอบแล้วมีผล

### Q8 — ชุด capability ของแต่ละ role อยู่ใน TypeScript ไม่ใช่ในตาราง

```ts
const ROLE_CAPABILITIES: Record<Role, ReadonlySet<Capability>> = { ... }
```

**นี่คือการล้ม master-spec §H.4 อย่างเป็นทางการ** ซึ่งสั่งไว้ที่ `master-spec.md:474` ว่า `role_permission = (role, resource_type, action, is_allowed, scope_filter)` พร้อมอัลกอริทึม 8 ขั้น และ *"Test matrix: 50+ cases mandatory before Sprint 0 ends"* ที่ไม่เคยเกิดขึ้น ตามกฎ source-of-truth precedence ADR ชนะ spec — และการล้มนี้ถูกประกาศออกมาตรง ๆ แทนที่จะปล่อยให้ขัดกันเงียบ ๆ

เหตุผลที่ชี้ขาด: **เราเพิ่งจ่าย 145 การแก้ไขเพื่อให้คอมไพเลอร์เป็นคนบังคับ (Q6)** ถ้าเอาชุดกฎไปไว้ในตารางฐานข้อมูล ชื่อ capability จะกลายเป็น string ที่ไม่มีอะไรตรวจ — พิมพ์ `cost:veiw` ผิดคือสิทธิ์นั้นเงียบหายไปโดยไม่มีอะไรแดง ครึ่งหนึ่งของสิ่งที่ Q6 ซื้อมาจะสูญทันที นอกจากนั้น ตารางที่ไม่มีหน้าจอแก้คือ **ตารางที่ไม่มีคนเขียน** ซึ่งคือบาปที่ ADR 0021 Q1 ตั้งชื่อไว้เอง

`role` เป็น `String` ไม่ใช่ enum (`schema.prisma:281`) → **เพิ่ม role ใหม่ทีหลังไม่ต้อง migration** ซึ่งเป็นความยืดหยุ่นที่คนอยากได้จริง

### Q9 — `own_record` ไม่อยู่ใน Part นี้ และ `scope_filter` ตายทั้งก้อน

มีสิทธิ์ + อยู่สาขานั้น = แก้เอกสารในสาขานั้นได้ทุกใบ

ไม่ใช่เพราะ "ไว้ทีหลัง" แต่เพราะ **ระบบนี้ตอบคำถาม "ใครทำ" ด้วยวิธีอื่นอยู่แล้ว และตอบได้ดีกว่า** — ทุกการยกเลิกเป็น append-only, void ไม่ได้ลบของ มันเขียน movement ชดเชยใบใหม่ที่มีผู้เขียนของตัวเอง ADR 0021 Q18 พูดเรื่องนี้ไว้เองตอนยอมไม่ทำ permissions: *"append-and-supersede ทำให้ทุกเวอร์ชันมีผู้เขียนและวันที่ของมัน"* — **ล็อกกันคนแก้ของคนอื่น กับ บันทึกว่าใครแก้ เป็นคนละเครื่องมือ** ร้านที่มีพนักงาน 8 คนต้องการ *ตามรอยได้* ไม่ใช่ *กันไม่ให้ทำ* และการล็อกจะสร้างปัญหาจริงทันที: คนเปิดใบนับสต๊อกไว้แล้วกลับบ้าน กะดึกปิดใบไม่ได้

`scope_filter` ของ H.4 จึงตายครบทั้งสามค่า: `own_dept` ที่ Q5 · `own_branch` กลายเป็น `canAccessBranch` · `own_record` ที่นี่

*(ปฏิเสธ: **ทำเท่าที่ข้อมูลมี** (5 ตารางที่มี `created_by`) — ผู้ใช้จะเจอกฎที่พูดออกมาเป็นประโยคไม่ได้: void ใบนับสต๊อกของเพื่อนได้ แต่แก้ใบค่าใช้จ่ายของเพื่อนไม่ได้ ไม่มีหลักการอยู่เบื้องหลัง มีแต่ประวัติศาสตร์ของ schema ปฏิเสธ: **เติม `created_by` ให้ครบ** — backfill ด้วยอะไรก็ไม่มีคำตอบ และรื้อมติ ADR 0028 Q4 ที่เพิ่งตัดสินไปสองวันก่อน)*

### Q10 — `member:manage` เป็น capability ธรรมดา และกฎกันไต่สิทธิ์ 4 ข้อไม่ต้องมีบันไดเลย

ให้ owner จัดการคนอยู่คนเดียวไม่ไหว ร้านที่มี 3 สาขาเจ้าของไม่มานั่งเชิญพนักงานเองทุกคน แต่ทันทีที่ role อื่นถือ `member:manage` ช่องไต่สิทธิ์ก็เปิด — และช่องจริงไม่ใช่ "เลื่อนขั้นตัวเอง" แต่คือ **เชิญอีเมลสำรองของตัวเองเข้ามาเป็น `owner` แล้วล็อกอินเป็นคนนั้น** ซึ่ง Q2 ทำให้ทำได้ใน 30 วินาที

กฎสี่ข้อ ไม่มีข้อไหนต้องเปรียบเทียบว่าใครสูงกว่าใคร:

| # | กฎ |
| --- | --- |
| **1** | แถวที่ role เป็น `owner` แก้ได้โดย `owner` เท่านั้น |
| **2** | มอบสิทธิ์สาขาได้เฉพาะสาขาที่ตัวเองเข้าถึง — `all_branches = false` มอบ `all_branches` ให้ใครไม่ได้ |
| **3** | ทุก tenant ต้องมี `owner` ที่ active อย่างน้อย 1 คนเสมอ |
| **4** | **มอบ role ได้เฉพาะ role ที่ชุด capability ของมันเป็นสับเซ็ตของตัวเอง** |

กฎ 4 คือครึ่งที่ใช้ได้ของแนวคิด "ห้ามให้สิทธิ์ที่ตัวเองไม่มี" — **การเป็นสับเซ็ตนิยามบนเซ็ตได้ตรง ๆ ไม่ต้องมีลำดับชั้น** ต่างจากครึ่ง "ห้ามแตะ role ที่สูงกว่า" ที่ต้องมี และถูกทิ้ง (Q4 ทำให้ role เป็นเซ็ตของ capability ไม่ใช่บันได — `purchaser` กับ `accountant` ใครสูงกว่ากันตอบไม่ได้ และไม่ควรตอบได้)

กฎ 4 ทำให้ **"มีแต่ owner ที่ให้ role `owner` ได้" กลายเป็นผลลัพธ์ ไม่ต้องเขียนเป็นกฎแยก** — สัญญาณว่ากฎนี้อยู่ถูกที่ และมันยังทำให้ **การแก้ role ตัวเองปลอดภัยโดยอัตโนมัติ**: ให้ตัวเองเท่าเดิมคือ no-op, ให้น้อยลงได้, ให้มากขึ้นไม่ได้ (กฎ 4) และถอด owner คนสุดท้ายไม่ได้ (กฎ 3)

**กฎ 3 เป็นการปฏิเสธจริง และมันไม่ใช่ข้อยกเว้นของหลัก ADR 0028** — ADR 0028 ไม่ห้ามสิ่งที่เป็นนโยบาย เพราะของกินไปแล้ว การปฏิเสธไม่ทำให้ของกลับมา แต่ **tenant ที่ไม่มี owner คือ tenant ที่ไม่มีใครแก้ไขอะไรได้อีกเลยตลอดไป** — ไม่มีหน้า admin ไม่มีเครื่องมือ support ไม่มีทางกู้ นี่คือ *inability* ตามนิยามเดิม ไม่ใช่นโยบาย

**`member:manage` ถือโดย `owner`, `admin`, `manager`** โดย `manager` ถูกกฎ 2 จำกัดให้จัดการคนได้เฉพาะสาขาที่ตัวเองเข้าถึง — และผู้จัดการเขต (`all_branches = true`) จึงจัดการคนได้ทั้งเขต **ฟรีจาก Q5b โดยไม่ต้องมีกลไกใหม่**

### Q11 — `admin` = `owner` ลบความเป็นเจ้าของ

role ทั้งหมด **7 ตัว**: `owner` · **`admin`** · `manager` · `purchaser` · `kitchen_staff` · `accountant` · `viewer`

`admin` มีอยู่เพื่อร้านที่มี **ส่วนกลาง** — `manager` ที่คุมครัวอยู่แล้วไม่ควรต้องรับงานจัดการบัญชีผู้ใช้ทั้งเครือด้วย `admin` ถือทุก capability ปฏิบัติการ ยกเว้น: แตะแถวที่เป็น `owner` ไม่ได้ (กฎ 1) · ให้ role `owner` ไม่ได้ (ตกจากกฎ 4 เอง) · ลบร้าน/บิลลิ่งไม่ได้

**กฎ 4 บังคับคำตอบนี้ ไม่ใช่เราเลือก** — `admin` ที่ถือแค่ `member:manage` + `settings:write` จะสร้าง `manager` ไม่ได้ เพราะ `manager` มี `cost:view` ที่เขาไม่มี เขาจะทำงานหลักของตัวเองไม่ได้ และนี่คือกฎ 4 กำลัง **บอกความจริง** ไม่ใช่กำลังกีดขวาง: *ใครก็ตามที่มอบสิทธิ์ให้คนอื่นได้ ย่อมมีสิทธิ์นั้นเองอยู่แล้วโดยปริยาย* เพราะเขาเชิญอีเมลตัวเองเข้ามาแล้วมอบให้ได้เสมอ **ระบบที่บอกว่า "แอดมินให้สิทธิ์ดูต้นทุนได้ แต่ตัวเองดูไม่ได้" คือระบบที่โกหกตัวเอง**

### Q12 — `cost:view` อยู่ที่ทางออกสู่หน้าจอ ไม่ใช่ที่เครื่องคิดต้นทุน

🔴 **ห้ามเอาด่านไปไว้ที่ 7 ทางเข้าของ `stock-cost.ts` / `recipe-cost.ts`** — มันไม่ได้ถูกเรียกเพื่อแสดงผลอย่างเดียว **มันถูกเรียกตอนเขียน ledger ด้วย**: คนครัวลงมื้อพนักงาน ระบบต้องตี FIFO เพื่อเขียน movement **คนครัวต้องคำนวณต้นทุนได้ โดยไม่มีสิทธิ์เห็นมัน**

> **คำนวณต้นทุน ≠ แสดงต้นทุน**

read ที่แสดงผลรับ **ตั๋ว** เป็นพารามิเตอร์บังคับ:

```ts
getRecipeListLogic(tenantId, { ..., cost: CostAccess | null })
```

`CostAccess` สร้างได้จากที่เดียวคือ `requireTenant` หลังเช็ค `cost:view` แล้ว — **ไม่ใช่ `boolean` ที่ใครก็ส่ง `true` ได้** `boolean` ไม่ใช่ด่าน มันคือคำขอ

จุดที่ต้องแก้จริงคือที่ `recipe-read.ts:504` และ `:741` ซึ่ง**ฝังต้นทุนไว้ในก้อนข้อมูลเดียวกับตัวสูตร** — วันนี้คนครัวเปิดหน้ารายการสูตรแล้วได้ต้นทุนติดมาเสมอ

*(ปฏิเสธ: **ให้ต้นทุนมีประตูของตัวเองประตูเดียว** โดยรื้อ `recipe-read` ให้คืนสูตรเปล่าแล้ว fetch ต้นทุนแยก — ย้ายปัญหาไปฝั่ง client และเปิดโหมดพังใหม่: ต้นทุนมาช้ากว่าตัวสูตรครึ่งวินาที คนอ่านเห็น `—` แล้วเชื่อว่าไม่มีต้นทุน ซึ่งเป็นบาปเดียวกับที่ `BranchCostTable.tsx:16` เขียนเตือนไว้เอง)*

### Q13 — ซ่อนสิ่งที่ใช้ไม่ได้ · ปฏิเสธที่เซิร์ฟเวอร์เสมอ · อธิบายเมื่อเดินมาถึงเอง

`src/app/dashboard/page.tsx` มีลิงก์ 19 อันเรียงกันอยู่ — **แดชบอร์ดคือเมนูนำทาง** และเป็นจุดเดียว ทำให้การกรองลิงก์ตาม capability ทำที่เดียวจบ ปุ่มที่กดไม่ได้ **ไม่เรนเดอร์** ไม่ใช่เรนเดอร์แล้วปิด ตาม precedent ที่เขียนไว้แล้วที่ `goods-receipts/[id]/edit/page.tsx:4` — *"ฟอร์มสีเทาเชิญให้ผู้ใช้ไปหาวิธีเปิดมัน ทั้งที่ไม่มีวิธีนั้น"*

สามข้อที่เป็นกฎ เพราะแต่ละข้อคือบั๊กที่จะเกิดถ้าไม่เขียนไว้:

1. **ซ่อนคือเรื่องความสะอาดของหน้าจอ ไม่ใช่ความปลอดภัย** — เซิร์ฟเวอร์ปฏิเสธเสมอ ไม่ว่าปุ่มจะโผล่หรือไม่ ห้ามมีที่ไหนที่ "ซ่อนแล้วเลยไม่ต้องเช็ค"
2. **ถูกปฏิเสธ ≠ ไม่มีข้อมูล** — ช่องต้นทุนที่ตัดออกด้วยตั๋วต้องอ่านออกว่า *ไม่มีสิทธิ์เห็น* ถ้าเรนเดอร์ `฿0` หรือ `—` จะถูกอ่านว่า *ต้นทุนเป็นศูนย์* หรือ *ยังไม่มีข้อมูล* — บาปเดียวกับที่ ADR 0025 ยืนยันว่าต้องพิมพ์ `null` ไม่ใช่ `0%`
3. **404 ห้ามใช้เป็นคำตอบของ "ไม่มีสิทธิ์"** — มันโกหกว่าหน้านั้นไม่มีอยู่ แล้วผู้ใช้จะไปแจ้งว่าระบบพัง

### Q14 — บันทึกการเปลี่ยนสิทธิ์ครั้งล่าสุด ไม่ใช่ทั้งประวัติ

`tenant_membership` เป็นแถวที่ UPDATE ทับ มีแค่ `updated_at` ไม่มี `updated_by` พอ Q10/Q11 ให้ `manager` และ `admin` เปลี่ยน role คนอื่นได้ คำถาม *"ใครถอดสิทธิ์ดูต้นทุนของฉันเมื่อวาน"* จะไม่มีคำตอบอยู่ในระบบเลย

**`role_changed_at` + `role_changed_by`** สองคอลัมน์บนแถวเดิม ขี่ไปกับ migration ของ `all_branches`

**ข้อพิพาทจริงเป็นเรื่องสถานะปัจจุบัน ไม่ใช่ประวัติศาสตร์** — คนไม่ได้ถามว่าสิทธิ์เปลี่ยนมากี่รอบ เขาถามว่า *"ทำไมตอนนี้ฉันเข้าไม่ได้ และใครทำ"*

ความต่างจาก Part 27 ที่ปฏิเสธคอลัมน์ไปสองตัว: ตอนนั้น `deactivated_at` ถูกปฏิเสธเพราะคำถามที่มันถูกซื้อมาตอบ **มีของอื่นตอบได้อยู่แล้ว** (วันขายล่าสุด) รอบนี้ตรงข้าม — ไม่มีอะไรในระบบตอบคำถามนี้ได้เลยแม้แต่นิดเดียว

*(ปฏิเสธ: **ตาราง `membership_change_log`** — ตารางใหม่ + RLS policy + `TENANT_SCOPED_DELETE_ORDER` + หน้าจออ่าน สำหรับ Part ที่ใหญ่เกินไปอยู่แล้ว)*

### Q15 — คอมไพเลอร์จับ "ลืมใส่ด่าน" · เทสต์จับ "ใส่ผิดตัว"

Q6 ทำให้การลืมใส่ด่านเป็น compile error ไปแล้ว เทสต์จึงไม่ต้องรับผิดชอบข้อนั้น สิ่งที่เทสต์ต้องจับคือสิ่งที่คอมไพเลอร์จับไม่ได้ — **ใส่ capability ผิดตัว** และ **ชุด capability ของ role ผิด**

- **unit** บนตัว `ROLE_CAPABILITIES` เอง: `viewer` ไม่มี `:write` ตัวไหนเลย · `owner` เป็นซูเปอร์เซ็ตของทุก role · ทุก role ที่ถือ `member:manage` ต้องผ่านกฎ 4 กับ role ที่มันควรสร้างได้
- **E2E action-stack ด้วย membership จริง** ต่อยอดจาก harness ที่มีอยู่

**หกอย่างที่ต้องเห็นแดงอย่างน้อยหนึ่งครั้งก่อนปิด:**

1. `viewer` กด `createStaffMealAction` → ปฏิเสธ (ledger ไม่ขยับ)
2. `manager` สาขาอโศก นับสต๊อกที่สาขาสีลม → ปฏิเสธ (กฎ 2 / Q5)
3. `manager` สาขาอโศก เชิญคนเข้าสาขาสีลม → ปฏิเสธ (กฎ 2 บนการมอบสิทธิ์)
4. `manager` เชิญอีเมลตัวเองเป็น `owner` → ปฏิเสธ (กฎ 4 — ช่องไต่สิทธิ์ตัวจริง)
5. `admin` ปลด `owner` คนสุดท้าย → ปฏิเสธ (กฎ 3)
6. `kitchen_staff` เปิดรายการสูตร → **ได้สูตร ไม่ได้ต้นทุน** และ **ลงมื้อพนักงานได้สำเร็จ**

ข้อ 6 คือคู่ที่ discriminate จริงตามบทเรียน Part 26 — ครึ่งแรกเขียวได้แม้ไม่มีกฎอะไรเลย **ครึ่งหลังต่างหากที่แดงทันทีถ้าเราวางด่านผิดชั้น** (Q12)

*(ปฏิเสธ: **registry กลาง + เทสต์เมทริกซ์** — capability ถูกประกาศสองที่ (call site กับ registry) เกิด drift และวันที่ไม่ตรงกัน registry จะเป็นฝ่ายผิดแต่เทสต์จะเชื่อ registry)*

### Q16 — ลงมือสอง Part เรียงกัน ออกแบบครั้งเดียว

- **Part 28 สิทธิ์** — Q4–Q9, Q12, Q13 + คอลัมน์ `all_branches` · เทสต์สร้าง membership ตรง ๆ ผ่าน Prisma
- **Part 29 เชิญคนเข้าร้าน** — Q2, Q3, Q10, Q11 + `role_changed_at`/`role_changed_by` · E2E เชิญจริง หกเคสของ Q15

⛔ **ลำดับกลับด้านเป็นสิ่งต้องห้าม** — ถ้าทำ 29 ก่อน เราจะส่งมอบความสามารถในการ *สร้างผู้ใช้ที่สิทธิ์น้อย* โดยที่ยังไม่มีด่านบังคับ = **แย่กว่าวันนี้จริง ๆ** ไม่ใช่แค่ไม่ดีขึ้น

การแยกนี้ต่างจากสิ่งที่ Q1 ปฏิเสธ: Q1 ปฏิเสธ *"ต่อสายด่านก่อน เรื่องเชิญคนค่อยว่ากัน"* แบบไม่มีกำหนดและไม่มีการออกแบบ ที่นี่ **29 ถูกออกแบบเสร็จแล้วใน ADR ฉบับเดียวกัน และถูกกำหนดให้ตามมาทันที**

## Schema

| ตาราง | คอลัมน์ที่เพิ่ม | หมายเหตุ |
| --- | --- | --- |
| `tenant_membership` | `all_branches Boolean @default(false)` | Q5b · owner ได้ `true` ที่ `tenant-init.ts` · แทนที่ owner bypass ที่ `service.ts:131` |
| `tenant_membership` | `role_changed_at DateTime?` | Q14 |
| `tenant_membership` | `role_changed_by String?` → `User` | Q14 |

ทั้งสามเป็น additive มี default/nullable — **ไม่ต้อง backfill** (แถวที่มีอยู่ทั้งหมดเป็น owner คนเดียวของ tenant ตัวเอง → migration ตั้ง `all_branches = true` ให้ role `owner`)

**ไม่มีตารางใหม่** · `role` ยังเป็น `String` → เพิ่ม role ใหม่ไม่ต้อง migration

## Consequences

1. **`ResourceType`, `Action`, `ROLE_PERMISSIONS`, `canPerform` ถูกลบ** — ของเดิมบรรยายระบบที่ไม่เคยถูกสร้าง (Context 3) การ "ซ่อม" มันจะเป็นการรับมรดกที่ไม่มีใครเคยใช้ `canAccessBranch` เขียนใหม่ตาม Q5b · `canAccessDepartment` และ `getUserContext` อยู่ต่อแต่ยังไม่ถูกเรียก และ **ต้องมีคอมเมนต์บอกว่าทำไม**

2. **master-spec §H.4 ตายทั้งหมด** — เมทริกซ์ `role_permission` (Q8) · อัลกอริทึม 8 ขั้น (Q6) · `scope_filter` ทั้งสามค่า (Q5, Q9) · test matrix 50 เคส (Q15) ต้องเขียนกำกับใน spec ว่าถูก ADR 0029 แทนที่ ไม่ใช่ปล่อยให้ขัดกันเงียบ

3. **RLS ไม่ถูกแตะ** — ADR 0004 เลื่อนการเปิดใช้ไป Sprint 7 และ ADR ฉบับนี้ไม่เปลี่ยนแผนนั้น **สิทธิ์กับการแยก tenant เป็นคนละชั้นและคนละปัญหา**: RLS กันร้าน A ไม่ให้เห็นข้อมูลร้าน B ส่วน ADR นี้กันคนในร้าน A เอง ทั้งคู่ยังจำเป็นทั้งคู่

4. **`/signup` ยังเป็นหน้าที่ไม่ต้อง login และ upsert ด้วยอีเมล** — Part 29 ไม่ได้แก้เรื่องนี้ ใครก็ยังสร้าง tenant ผูกกับอีเมลของคนอื่นได้ (เจ้าของอีเมลตัวจริงจะได้ membership ใบที่สองที่เขาไม่ได้ขอ) ผลกระทบถูกจำกัดด้วย magic link — ต้องเป็นเจ้าของอีเมลถึงจะเข้าได้ — และด้วยหน้าเลือกร้านของ Q3 ที่ทำให้ membership แปลกปลอมมองเห็นได้แทนที่จะเงียบ **แต่มันเป็นหนี้ที่ยังไม่ถูกจ่าย**

5. **`viewer` มีตัวตนจริงเป็นครั้งแรก** — และเป็น role เดียวที่ไม่มี capability เขียนเลยสักตัว เทสต์ข้อ 1 ของ Q15 คือครั้งแรกที่มีการพิสูจน์ว่ามันหมายถึงอะไร

6. **หนี้ที่ Part 26/28 ทิ้งไว้ยังไม่ถูกแตะ** — `staff_member` กับสี่ช่อง `*_by_name` (ADR 0028 Q4) · `sales_line.discount_reason` ที่ยังไม่มีใคร map (ADR 0028 Q6) ทั้งคู่ไม่ใช่คำถามเรื่องสิทธิ์และไม่ควรถูกดึงเข้ามา

7. **145 คือขนาดที่แท้จริงของงานนี้** ไม่มีเวอร์ชันถูกกว่านี้ที่ซื่อสัตย์ — ADR 0021 Q18 ปฏิเสธเวอร์ชันถูกไปแล้วครั้งหนึ่ง ด้วยเหตุผลที่ ADR ฉบับนี้ยังยึดอยู่
