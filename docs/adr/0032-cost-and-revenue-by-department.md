# ADR 0032 — ต้นทุนและรายได้ต่อแผนก: ป้ายอยู่บนเมนู ยอดรวมอยู่บน ledger และของหายไม่มีเจ้าของ

**Status:** accepted · **Date:** 2026-09-01 · **Grill:** Q1–Q7
**Part:** Sprint 7 Part 32 · **Supersedes in part** master-spec §Section F และ §H.8 · **Pays** ADR 0022 Q8 (การแยกแผนกที่ถอนออกไปตอน Part 22) · **ไม่มี migration ไม่แตะ ledger**

## Context

Kong พูดไว้ตรง ๆ ระหว่าง grill ว่า *"ยังไงก็ต้องมีแผนก มันคือสิ่งที่เราต้องการตั้งแต่แรก — cost รายได้ตามแผนก ที่เราจะ diag ปัญหาของการจัดการร้านได้"* นี่ไม่ใช่ฟีเจอร์เสริม มันคือเหตุผลที่ระบบนี้มีอยู่ และ ADR นี้เขียนขึ้นหลังจากผู้เขียนเสนอ "ตัดแผนกทิ้ง" แล้วถูกปฏิเสธอย่างถูกต้อง

ข้อเท็จจริงแปดข้อจากสคีมาและโค้ด ไม่ใช่จากความจำ

1. **`departmentId` มีอยู่จริงสี่ที่ และทั้งสี่อยู่ฝั่ง "ของเข้า/เงินออก"** — `PurchaseOrderItemAllocation` · `GoodsReceiptItemAllocation` · `ExpenseItem` (nullable) · และ `Menu.primaryDepartmentId` (nullable) กับ `UserDepartmentAssignment`

2. **ฝั่ง "ของออก" ไม่มีเลย** — `StockMovement` มีแค่ `branchId` · `SalesConsumptionItem` = `tenantId` + `runId` + `productId` + `qty` **ไม่มี `menuId`** เพราะ ADR 0022 ระเบิดเมนูเป็นวัตถุดิบตอน post

3. **`tenant.enableDepartments` default `false`** และเมื่อเปิด `/menus` **ขึ้นเตือนให้กรอกแผนกอยู่แล้ว** (`NEEDS_DEPARTMENT` ใน `menu-view.ts:75`) — ฝั่งรายได้จึงต่อสายไว้เรียบร้อยตั้งแต่ Part 19

4. **`tenant.grossProfitMethod` default `PERIODIC_INVENTORY`** (นับสต๊อก = ต้นงวด + ซื้อ − ปลายงวด) อีกค่าคือวิธีสูตรอาหาร

5. **`StockCountItem` เก็บทั้งสองฝั่งของส่วนต่างไว้แล้ว** — `qtyCounted` และ `qtyExpected` (snapshot ของยอด ledger ตอนบันทึกบรรทัดนั้น) และส่วนต่างคำนวณตอนอ่าน ไม่เก็บเป็นข้อเท็จจริงที่สาม

6. **`/cost` มีครบแล้วต่อสาขา** — ต้นทุนวัตถุดิบ (ของที่ซื้อเข้า) · ของเสีย · **ส่วนต่าง/ปรับปรุง** (*"ของที่หายไปโดยไม่มีใครบันทึก"*) · รายได้ · ต้นทุนของที่ขายไป · กำไรขั้นต้น

7. **§H.8 ของ master-spec เขียน SQL บนคอลัมน์ที่ไม่เคยมี** — `stock_movement.department_id` — และตั้งอยู่บนสมมติฐานว่า "ทฤษฎี" ต้องคำนวณแยกเพราะไม่ได้อยู่ใน ledger **ซึ่ง Part 22 ทำให้เป็นเท็จไปแล้ว**

8. **§Section F ขอ "Cost" ต่อช่อง แผนก × สาขา แบบรวม ๆ** โดยไม่แยกว่าเป็นต้นทุนวัตถุดิบหรือค่าใช้จ่ายดำเนินงาน

## Decision

### Q1 — ป้ายบอกแผนกคือ **เมนู** และไม่ต้องเก็บอะไรเพิ่มเลย

ช่องว่างมีจุดเดียว ไม่ใช่ทั้งระบบ:

| ต้องการ | มีแล้วหรือยัง |
|---|---|
| รายได้ต่อแผนก | ✅ `sales_line` → `menu.primaryDepartmentId` |
| ของที่ซื้อเข้าต่อแผนก | ✅ `GoodsReceiptItemAllocation.departmentId` |
| OpEx ต่อแผนก | ✅ `ExpenseItem.departmentId` |
| **ของที่ถูกใช้ไปต่อแผนก** | ❌ **จุดเดียวนี้** |

**สี่ทางที่พิจารณา:**

- **A — `department_id` บน `stock_movement`** ❌ `fifo-replay.ts` อ่านตารางนี้ทุกครั้งที่คิดต้นทุน มันคือทางที่ร้อนและถูกระวังที่สุดในระบบ และ ADR 0011 ออกแบบให้ ledger โง่โดยตั้งใจ — **แผนกคือ "ทำไม" ไม่ใช่ "อะไรที่เคลื่อน"** และ "ทำไม" อยู่บนเอกสารเสมอ
- **B — ไม่มีมิติแผนกเลย** ❌ **ผู้เขียนเสนอข้อนี้และมันผิด** สามในสี่เสาต่อยอดได้ทันทีอยู่แล้ว การตัดทิ้งเพราะเสาที่สี่ขาดคือการทิ้งของที่มีอยู่แล้วสามในสี่
- **C — `departmentId` บน `SalesConsumptionItem`** ❌ ไม่ผิด แต่**เกินจำเป็น** — ถูกแทนที่หลัง Kong ชี้ว่าข้อมูลมีอยู่แล้ว
- **D — คำนวณตอนอ่าน** ✅ **เลือกข้อนี้**

**D ทำงานได้เพราะข้อมูลครบอยู่แล้วทั้งสาย:**

```
sales_line  (วันไหน · สาขาไหน · เมนูอะไร · กี่จาน)
   → menu.primaryDepartmentId      ← ป้ายบอกแผนก
   → recipe ที่ resolve ตามวันนั้น  ← วัตถุดิบกี่กรัม
   → FIFO replay                    ← ราคาต่อกรัม
```

ไม่เก็บอะไรลงฐานข้อมูลเลย เหมือนที่ ADR 0014 ทำกับต้นทุนมาตลอด 31 Parts (*cost is stored nowhere*) และ ADR 0022 ก็อ่าน "run ที่ยังยืนอยู่" ด้วยเหตุผลเดียวกัน

### Q2 — **ยอดรวมมาจาก ledger การแบ่งมาจากเมนู** — กฎข้อเดียวที่ทั้ง Part ยืนอยู่บนมัน

สามขั้น และลำดับสำคัญ:

1. **ยอดจริง** — ถามจาก run ที่ยังยืนอยู่: *ส.ค. ที่ทองหล่อ ตัดมะนาวไป 38 kg มูลค่า FIFO ฿3,040*
2. **สัดส่วน** — คำนวณจากยอดขาย × สูตร: ยำ 200×40g = 8 kg (21%) · โซดามะนาว 500×60g = 30 kg (79%)
3. **หาร** — ครัว ฿640 · บาร์ ฿2,400 · **รวม ฿3,040 เท่าเดิมโดยนิยาม**

**ทำไมไม่คำนวณใหม่ทั้งก้อนจากสูตร:** สูตรถูกแก้ ปัดเศษ หรือโพสต์ซ้ำ ทำให้ผลที่คำนวณใหม่ไม่ตรงกับที่ ledger เคลื่อนจริงได้ แล้วคอลัมน์แผนกจะบวกกันไม่เท่ากับ COGS จริง **วิธีนี้บวกกันได้ยอดจริงเสมอ เพราะมันคือการหารยอดจริง ไม่ใช่การคิดยอดใหม่**

### Q3 — ต้นทุนต่อแผนกมีสองตัว ไม่เท่ากัน และห้ามบวกกัน

- **ของที่ซื้อเข้าให้แผนก** (GR allocation) — ตอบว่าใครสั่งของ ใครทำงบซื้อบานปลาย
- **ของที่แผนกใช้ไปจริง** (consumption) — **นี่คือตัวที่คู่กับรายได้เป็นกำไรขั้นต้น**

Kong อธิบายส่วนต่างไว้ครบกว่าที่ผู้เขียนเสนอ: ซื้อ ฿24,000 ใช้ ฿20,080 ส่วนต่าง ฿3,920 คือของที่ทบไป **ทำให้ต้นทุนของ *เดือนนี้* ต่ำลง** และเดือนหน้าที่กินของก้อนนั้นโดยไม่ได้จ่ายเงินซื้อ **ต้องบวก ฿3,920 กลับเข้าไปในต้นทุนเดือนหน้า**

```
ต้นทุน = ของต้นงวด + ซื้อ − ของปลายงวด
ส.ค.    0     + 24,000 − 3,920 = 20,080   ← เท่ากับที่สูตรบอกว่าใช้ไป
ก.ย.    3,920 + ซื้อ   − 0     = ซื้อ + 3,920
```

**สองวิธีคิด GP ที่ระบบมีอยู่ต้องบรรจบกันเสมอ และวันที่มันไม่บรรจบคือวันที่มีของหายที่ไม่มีใครบันทึก** — ซึ่งคือสิ่งที่ Q6 ไปจับ

### Q4 — GP ต่อแผนกทำได้เฉพาะวิธี "สูตรอาหาร" เท่านั้น

วิธี **นับสต๊อก** (ค่าเริ่มต้นของทุกร้าน) แยกตามแผนกไม่ได้ เพราะ **ของที่เหลือในสต๊อกอยู่ในห้องเก็บของของสาขา ไม่ได้อยู่ในแผนกไหน** — ไม่มีทางบอกได้ว่าข้าวสาร 12 กระสอบที่เหลือเป็นของครัวกี่กระสอบ

ผลที่ต้องพูดบนหน้าจอ ไม่ใช่ซ่อน: **ร้านที่ไม่มีสูตร จะได้รายได้ต่อแผนกและ OpEx ต่อแผนก แต่ไม่มีกำไรขั้นต้นต่อแผนก**

### Q5 — matrix คือ **ต้นทุนวัตถุดิบ + รายได้** เท่านั้น ค่าไฟค่าเช่าไม่เข้า

§Section F เขียนคำว่า "Cost" ต่อช่องแบบรวม ๆ **และตรงนั้น spec หลวม** ค่าไฟค่าเช่าเป็นค่าใช้จ่ายในการดำเนินงานของทั้งร้าน การหารมันเข้า food cost % ทำให้ตัวเลขที่ร้านอาหารทุกร้านใช้เทียบกันไม่มีความหมาย

- **matrix** = ต้นทุนวัตถุดิบ + รายได้ + กำไรขั้นต้น ต่อ แผนก × สาขา
- **OpEx ต่อแผนก** = รายงานคนละใบ (`ExpenseItem.departmentId` ที่มีอยู่แล้ว)
- **ของที่แชร์กัน** (`departmentId` เป็น NULL) อยู่แถว "ส่วนกลาง" และ **ไม่ถูกหารเข้าแผนกโดยอัตโนมัติ** — §Section F เองก็เขียนว่า MVP ให้คนดูเอง

### Q6 — §H.8 ตายไปแล้วครึ่งหนึ่ง และอีกครึ่งถูกสร้างไปแล้วโดยที่ spec ไม่รู้

spec เขียน H.8 ตอนที่ยังไม่มีการตัดสต๊อกตามสูตร "ทฤษฎี" จึงต้องคำนวณแยก **แต่ Part 22 ทำให้สูตรตัดสต๊อกลง ledger จริง — ยอดใน ledger *คือ* ยอดทฤษฎี** และการนับสต๊อกคือของจริง ซึ่ง Part 15 เก็บไว้ทั้งสองฝั่งแล้ว (ข้อเท็จจริง 5)

เหลือแค่**มุมมอง**:

| มีแล้ว | ยังไม่มี |
|---|---|
| ส่วนต่างต่อการนับแต่ละครั้ง | ส่วนต่างสะสมต่อช่วงเวลา |
| ส่วนต่างเป็นยอดรวมของสาขา | **ส่วนต่างรายวัตถุดิบ** ว่าตัวไหนรั่ว |
| เรียงตามชื่อ | **เรียงตามเงิน** ตัวที่รั่วแพงที่สุดอยู่บนสุด |

### Q7 — ส่วนต่างไม่ถูกหารเข้าแผนก และนี่คือการปฏิเสธที่ตั้งใจ

หมูที่หายไป 13 กก. **ไม่มีใครบอกไว้ว่ามันหายจากมือใคร** การเอาสัดส่วนการใช้ไปหารแล้วพิมพ์ว่า *"ครัวทำของหาย ฿3,250"* คือการวางตัวเลขที่เดาลงในช่องที่คนอ่านจะเข้าใจว่าเป็นข้อเท็จจริง — **มันคือการกล่าวหาที่ข้อมูลไม่รองรับ**

ต่างจากต้นทุนและรายได้ ซึ่ง**หารได้อย่างมั่นใจเพราะเมนูบอกไว้ชัด**

แทนที่จะหาร รายงานพิมพ์ว่า**แผนกไหนใช้วัตถุดิบตัวนั้นบ้างและสัดส่วนเท่าไร** เจ้าของอ่านแล้วรู้เองว่าต้องไปถามใคร โดยระบบไม่ตัดสินแทน — **เป็นข้อมูล ไม่ใช่คำตัดสิน**

| วัตถุดิบ | ควรเหลือ | นับได้ | ขาด | มูลค่า | แผนกที่ใช้ |
|---|---|---|---|---|---|
| หมูสามชั้น | 18 kg | 5 kg | −13 kg | **−฿3,250** | ครัว 100% |
| มะนาว | 12 kg | 11 kg | −1 kg | −฿80 | บาร์ 79% · ครัว 21% |

## Consequences

1. **ไม่มี migration ไม่แตะ ledger ไม่แตะ Part 22** ทั้ง Part — และนั่นเป็นผลของ Q1 ไม่ใช่เป้าที่ตั้งไว้ก่อน

2. **เปลี่ยนแผนกของเมนู = รายงานย้อนหลังเปลี่ยนตาม** เพราะไม่มีอะไรถูกเก็บ · เป็นรูปแบบเดียวกับ ADR 0026 (*รายงานพับย้อนหลังเสมอ ledger พับตั้งแต่ `effective_from`*) และรับได้ด้วยเหตุผลเดียวกัน: รายงานไม่เก็บอะไร จึงกลับคำได้ทันที ส่วน movement ทำไม่ได้

3. **ของเสียและการปรับสต๊อกมือจะอยู่ "ไม่ระบุแผนก" เสมอ** เพราะไม่มีเมนูให้สาวกลับ · การเพิ่ม `departmentId` ลง `waste_log` ทำได้ทีหลัง — **คอลัมน์เดียวบนเอกสาร ไม่ใช่บน ledger** ตามหลักการเดียวกับ Q1 — และ**จงใจไม่ทำตอนนี้** เพราะยังไม่มีร้านจริงบอกว่าเขาแยกของเสียตามแผนกจริงไหม

4. **ร้านที่ปิดแผนกเห็นทุกอย่างเหมือนเดิมทุกประการ** — `enableDepartments` default `false` และทุกแถวเป็น "ไม่ระบุ" ซึ่งคือหน้าตาวันนี้

5. **เมนูที่ไม่ระบุแผนกไม่หายไปไหน** — ทั้งรายได้และต้นทุนของมันไปอยู่แถว "ไม่ระบุ" ให้เห็น ไม่ใช่ถูกตัดออกจากตัวหาร (เหตุผลเดียวกับ ADR 0027 ที่นับเมนูเลิกขายเต็มจำนวน)

6. **ความครอบคลุมยังต้องเดินคู่กับตัวเลขเสมอ** (ADR 0022) — GP ต่อแผนกที่มาจากสูตร ต้องพิมพ์ % ความครอบคลุมข้างกัน ห้ามพิมพ์เปล่า

7. **master-spec ต้องถูกปรับสองที่** — §Section F (คำว่า "Cost" ที่รวม COGS กับ OpEx เข้าด้วยกัน) และ §H.8 (SQL ที่อ้าง `stock_movement.department_id` และสมมติว่าทฤษฎีไม่ได้อยู่ใน ledger) 🛑 **แก้ spec ต้องถาม Kong ก่อนตามกฎ CLAUDE.md**

8. **Part 32 เล็กกว่าที่ตั้งไว้ตอนเริ่ม grill มาก** — สามชิ้น: มิติแผนกบนต้นทุน+รายได้ (ต่อยอด `/cost`) · รายงานของรั่วรายวัตถุดิบเรียงตามเงิน · หน้า Dashboard รวม

9. **ชิ้นที่สาม ("หน้า Dashboard รวม") ถูกยกเลิกตอนสร้าง — 2026-09-01, บันทึกไว้ไม่ใช่เงียบ ๆ ทิ้ง.** ตัวเลขต่อแผนกและตัวเลขของรั่วต่างต้องใช้ **FIFO replay ทั้งชุด** และ `/dashboard` คือหน้าที่ทุกคนเปิดก่อนเสมอ วันละหลายครั้ง — เอาขึ้นไปคือให้ทุกคนจ่ายค่าคำนวณหนักที่สุดของระบบทุกครั้งที่เปิดแอป **ซึ่งเป็นเหตุผลเดียวกับที่ Q1 แยก `/cost/departments` ออกมาเป็น route ของตัวเอง แต่หนักกว่าเดิม** · สิ่งที่ส่งมอบแทนคือ **สองหน้าจอ + ทางเข้าในเมนู** ที่กรองด้วย `cost:view`
   ถ้าวันหนึ่งอยากได้ตัวเลขสรุปบน dashboard จริง ๆ เงื่อนไขคือต้องมีที่เก็บผลที่คำนวณไว้แล้ว ซึ่งขัดกับ ADR 0014 (*cost is stored nowhere*) — เป็นการตัดสินใจของ Part อื่น ไม่ใช่ของ Part นี้
