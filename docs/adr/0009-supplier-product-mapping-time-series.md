# Supplier-Product Mapping: time-series price list with cascade-with-user-control

A `SupplierProductMapping` is a tenant-scoped, branch-aware price-list row linking a `Supplier` to a `Product`: the supplier's own item code/name, the `orderUnit` (a `ProductUnit` of that product — the unit it is purchased in), `currentUnitPrice`, and procurement terms (`minOrderQty`, `leadTimeDays`, `isPreferred`), valid from `effectiveFrom`. Part 8 captures this as an **append-only time-series**: entering a new price *supersedes* the previous row (its `effectiveTo` closes) instead of overwriting it, so historical prices survive for later cost / stock-value reconstruction. Ten modelling questions were locked in a grill (Q1–Q10): `effectiveFrom` becomes **NOT NULL** with an effective-today default (Q1) and both effective dates become Postgres **`date`** not `timestamp` (Q2) — the "when was this entered" audit question is already answered by `createdAt`, so the effective columns carry only the calendar grain the business actually has; a product maps to **unbounded** suppliers and **`isPreferred` is at most one per (product, branch-scope)**, enforced app-side exactly like 7b's `isDefaultBuyUnit` "move-the-flag" pattern (Q3); the series **blocks overlapping date ranges** and **allows future-dated** rows, with `effectiveTo = null` meaning "current / open until superseded" (Q4); `orderUnit` must be a **live unit of the mapping's product**, and a `ProductUnit` referenced by a live mapping **cannot be removed** — the ADR 0005/0006 "referenced-by-mapping" guard, now active (Q5); soft-deleting a `Supplier` or `Product` **cascades** to its mappings, but only after the user is shown the **blast-radius count** (Q6); a **branch override** (`branchId` set) **wholly replaces** the tenant default (`branchId` null) for that branch, resolved branch-first-then-default (Q7); prices/terms validate with price **optional ≥ 0**, min-order `> 0`, lead-time `0–365`, codes length-capped (Q8); scope is **data-capture only**, **product-centric** UI, with a minimal price-history viewer, the PO / cost-engine consumer **deferred to Sprint 2** (Q9); and the Prisma `@@unique` is replaced by a manual **PARTIAL unique index** `WHERE deleted_at IS NULL` with **`NULLS NOT DISTINCT`**, so soft-deleted rows never block re-create (Pitfall #22/#23) and duplicate tenant-defaults (NULL `branchId`) are still caught (Q10). Chosen because the schema already committed to a time-series shape (`effectiveFrom` in the unique key, a nullable `effectiveTo`), price history has real SME value (spotting a vendor's creep), and "deleting" in a financial system should **hide, never destroy** — soft-delete keeps the audit trail while cascade-with-confirm keeps active lists and Sprint-2 purchase ordering uncluttered without ever silently losing a record.

## Considered Options

- **(a) Cascade-with-user-control — soft-delete mappings when the parent is soft-deleted, but surface the blast-radius count and require a confirm (chosen)** — combines the convenience of cascade (delete a discontinued product, its supplier prices stop cluttering PO pickers) with visibility (the delete dialog reads "สินค้านี้มี N รายการราคาซัพพลายเออร์ — ลบแล้วจะถูกซ่อนด้วย"). Because every delete is soft, nothing is destroyed: rows stay queryable via the "All" filter and the history viewer (Q9b), and the Sprint-2 PO consumer simply filters `deletedAt IS NULL`. Diverges from 7c's BLOCK (ADR 0007) **by design** — a PREPPED child is an *independent entity* with its own units/recipes and must not vanish under its parent, whereas a mapping is a *dependent detail* of a supplier–product pair; the coherent rule is "blocking-dependents that are independent entities, hide-with-warning dependents that are details." The confirm dialog supplies the visibility that raw cascade lacked.
- **(b) Silent cascade — soft-delete mappings with no warning (rejected)** — same data effect as (a) but the user never sees the blast radius. Rejected because in a financial dataset a hidden group-delete (one click silently hides 10 price records) violates the "destructive op must be visible" principle (ai-collaboration stop-conditions), and with no restore-in-MVP a mistaken delete is effectively permanent. (a) is (b) plus one count query and a confirm string — cheap insurance.
- **(c) Block delete while any live mapping exists — mirror 7c's `ProductHasChildrenError` (rejected)** — maximally consistent and safe, but too rigid for the most common case: a restaurant *discontinues* a product or stops using a supplier and expects the record to retire quietly. Blocking forces the user to manually hunt down and delete every mapping first — tolerable for a product (its mappings live on its own product-centric page, Q9a) but painful for a supplier whose mappings are scattered across many product pages. Kept as the future escalation if cascade-with-confirm ever proves too loose (it is forward-compatible — tightening cascade → block does not migrate data).
- **(d) Hard-delete mappings on parent delete (rejected)** — physically removing the rows. Rejected outright: it breaks the financial **audit trail** (no record that "we used to buy salmon from Makro at ฿X"), and any historical stock-value or cost computation that re-reads a past price would skew or error once the row is gone. Soft-delete is the only option compatible with the time-series intent.

## Consequences

- **One Part 8 migration covers three schema edits** (`part_8_supplier_product_mapping`): `ALTER COLUMN effective_from SET NOT NULL` (Q1), `ALTER COLUMN effective_from/effective_to TYPE date` (Q2), and `DROP` of the Prisma-generated full unique index. The PARTIAL unique index ships separately as manual SQL in `prisma/manual/supplier_product_mapping_unique.sql` (Prisma 5.22 cannot express a `WHERE` clause on a unique index — same reason as `supplier_code_unique.sql`), applied via `prisma db execute` over `DIRECT_URL`. Greenfield (zero rows) so all edits are non-destructive.
- **Uniqueness / integrity is layered like 7d** (defense in depth, though not an XOR): zod validates field ranges + the time rules (Q8, Q4); the `*Logic` layer enforces what the DB cannot express — overlap-block across date ranges, `orderUnit ∈ product(live)`, and the `isPreferred` singleton (Q3/Q4/Q5); and the DB **partial unique index** (`NULLS NOT DISTINCT WHERE deleted_at IS NULL`) is the final backstop catching exact-key duplicates including two NULL-`branchId` tenant-defaults. A P2002 maps to a Thai error ("รายการซัพพลายเออร์นี้มีอยู่แล้วในช่วงวันที่นี้").
- **Append + supersede time-series**: a new price for an existing (supplier, product, branch) closes the prior row's `effectiveTo` and inserts a fresh open row (`effectiveTo = null`). Overlapping ranges are **rejected**; **future-dated** rows are allowed (the "current price" lookup `WHERE today BETWEEN effective_from AND COALESCE(effective_to,'infinity') ORDER BY effective_from DESC LIMIT 1` simply ignores them until their day arrives). The exact-key partial index only catches identical `effective_from`; range-overlap is an app-layer check (a Postgres `EXCLUDE` constraint was considered over-engineered for MVP).
- **Orphan mappings are tolerated by design**: the schema does not enforce referential *liveness*, so a mapping row can outlive a soft-deleted parent. The default delete path cascade-soft-deletes them (Q6), but because the data layer permits the orphan state, a future "keep this price active even though the product is retired" control is cheap, and soft-deleted rows are surfaced through an "All" list filter rather than being unreachable. No read path is allowed to crash on an orphan — joins tolerate a soft-deleted parent.
- **Sprint-2 PO consumer MUST snapshot the mapping at order time, not hold a live FK lookup** — copy `currentUnitPrice` / `orderUnit` onto the PO line when the order is placed. A live lookup would let a later supersede (Q4) or a cascade soft-delete (Q6) silently rewrite the historical stock value of an already-placed order. This ADR records the requirement so the procurement slice does not re-derive it.
- **`isPreferred` is an app-managed singleton, not a DB constraint** — at most one preferred mapping per (product, branch-scope) among live rows, moved by the `*Logic` layer when a new one is set (mirrors 7b `isDefaultBuyUnit`). A DB partial unique was rejected because the time-series (many rows per supplier) plus soft-delete make the correct grain brittle.
- **Restore-on-recreate is deferred to a Part 8.5 slice** — un-soft-deleting a Product (or Supplier) and having its previously-cascaded mappings come back is a **Product-layer lifecycle** concern, not a mapping-layer one, and MVP has no restore UI at all. Recorded as a deferred slice in sprint-progress so it is not silently assumed present.
