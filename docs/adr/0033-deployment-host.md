# ADR 0033 — ที่อยู่ของโปรดักชัน: สิงคโปร์เท่านั้น เครื่องเดียวรันค้าง และการเลือกที่ตั้งใจให้ย้อนกลับได้

**Status:** accepted · **Date:** 2026-09-03 · **Grill:** Q1–Q13
**Part:** Sprint 7 Part 34 · **ปลดล็อก** rate limit ชั้น 2 (ค้างจาก ADR 0031 Q6) และ `enforce_rls.sql` บน branch โปรดักชัน (ค้างจาก ADR 0030) · **ไม่มี migration**

## Context

การเลือก host ถูกบันทึกว่าเป็น blocker มาตั้งแต่ปิด Sprint 7 และไม่มี ADR รองรับ มันบล็อกทุกอย่างที่เหลือบนเส้นทางสู่ beta: rate limit ชั้น 2 ออกแบบไม่ได้จนกว่าจะรู้ว่า edge เป็นของใคร · `AUTH_URL` ยังเป็น `localhost` · และคำเชิญของ Part 29 จึงยังใช้ไม่ได้แม้จะเขียนเสร็จไปแล้ว

ข้อเท็จจริงสิบข้อจากโค้ดและจากเอกสารของผู้ให้บริการ วัดเมื่อ 2026-09-03 ไม่ใช่จากความจำ

1. **runtime ต้องเป็น Node เท่านั้น** — `@prisma/client` ถูก import 100 จุด · nodemailer · next-auth · `@auth/prisma-adapter` · และ **ไม่มี `export const runtime` สักที่ในโปรเจกต์** ทุกอย่างจึงเป็น nodejs โดยปริยาย · edge runtime รันไม่ได้

2. **ไม่มีงานเบื้องหลังเลย** — ไม่มี cron ไม่มี queue ไม่มี worker

3. **ไม่ต้องมีดิสก์ถาวร** — ไฟล์ CSV ที่อัปโหลดถูกอ่านเข้าหน่วยความจำด้วย `arrayBuffer()` (`sales/actions.ts:145`) ไม่เคยเขียนลงดิสก์ · แต่ต้องรับ request ได้ถึง **15 MB** (`MAX_SALES_FILE_BYTES`)

4. **API route ทั้งแอปมีตัวเดียว คือ Auth.js** — ไม่มี webhook ไม่มี endpoint ให้ POS ยิงเข้า ไม่มี realtime · ยอดขายเข้าเป็นไฟล์ที่คนอัปโหลด (ADR 0019) · **ไม่มีเครื่องจักรตัวไหนพึ่ง Mise อยู่**

5. **Neon อยู่ `ap-southeast-1`** (AWS สิงคโปร์) ทั้ง pooled และ direct

6. **ทุกการอ่านเปิด interactive transaction** — `runTenantTransaction` ทำ BEGIN → `set_config` → คิวรี → COMMIT ทุกครั้ง อย่างน้อย 3 round trip บวกจำนวนคิวรี และถูกเรียกจาก **174 จุด**

7. **โปรดักชันไม่มี singleton ของ Prisma** — `db.ts:167` ตั้ง `global.prismaGlobal` เฉพาะเมื่อ `NODE_ENV !== "production"` · ทุกโปรเซสจึงสร้าง client และ pool ของตัวเอง

8. **มี manual SQL 19 ไฟล์ที่ migration ไม่ได้ครอบคลุม** — 18 ไฟล์ idempotent · `enforce_rls.sql` ไม่ใช่ เพราะบรรทัด 48 คือ `CREATE ROLE mise_app WITH LOGIN PASSWORD 'REPLACE_ME_BEFORE_RUNNING'` · **ไม่มีอะไรใน repo อ้างถึงโฟลเดอร์นี้เลย** ไม่มีสคริปต์ ไม่มีลำดับที่เขียนไว้

9. **ไม่มี error boundary สักไฟล์** — ไม่มี `error.tsx` `global-error.tsx` `not-found.tsx` `loading.tsx` · และมี `throw new Error(` ดิบ 8 จุดใน `src/app` กับ `src/server`

10. **Neon แพลนฟรีดับ compute หลังว่าง 5 นาที และปิดไม่ได้** · เก็บประวัติย้อนหลัง **6 ชั่วโมง**

## Decision

### Q1 — host ต้องอยู่ `ap-southeast-1` และเป็นเงื่อนไขคัดตัวเลือก ไม่ใช่ข้อดี

ข้อเท็จจริง 6 คูณกับระยะทางกลายเป็นตัวเลขที่ตัดสินเอง หน้าหนึ่งที่เรียก `withTenantContext` ไม่กี่ครั้งใช้ราว 15 round trip

| host | RTT | หนึ่งหน้า |
|---|---|---|
| สิงคโปร์ | ~1–3 ms | ~40 ms |
| สหรัฐฯ ตะวันออก | ~230 ms | **~3.5 วินาที** |

**ค่า default ของ Vercel คือ `iad1`** — deploy โดยไม่ตั้ง region แล้วแอปจะช้าสามวินาทีต่อหน้า และมันจะดูเหมือนโค้ดห่วย ทั้งที่เป็นเรื่องระยะทางล้วน ๆ

**ปฏิเสธ:** ย้าย Neon ไปใกล้ host แทน — ลูกค้าอยู่ไทย ยิ่งย้าย DB ออกจากภูมิภาคยิ่งแย่ทั้งสองด้าน

### Q2 — เซิร์ฟเวอร์ Node รันค้างตัวเดียว ไม่ใช่ serverless

รูปแบบ "เปิด transaction ต่อการอ่านหนึ่งครั้ง" (ข้อ 6) **คือรูปแบบที่ serverless + pgbouncer รับได้แย่ที่สุดพอดี** และข้อ 7 แปลว่าทุก cold start คือ pool ใหม่ ซึ่งคือเครื่องผลิต connection เย็น — สิ่งที่ ADR 0024 วัดไว้ว่าค้าง ~0.3% และค้างถาวร

และเราไม่ได้อะไรกลับมาแลกเลย (ข้อ 2 และ 4) · ระบบหลังร้านมีคนใช้ไม่กี่คน ซึ่งแปลว่า **ถ้า scale-to-zero เกือบทุกครั้งที่เปิดหน้าจะเป็น cold start**

**ราคาที่จ่าย:** จ่ายตลอดเวลาแม้ไม่มีคนใช้ และมีเครื่องที่ต้องดูแลตอนล่ม

### Q3 — เขียน Dockerfile เอง

เหตุผลที่หนักกว่าข้ออื่นรวมกันไม่ใช่เรื่องเทคนิค แต่คือ **มันทำให้การเลือกเจ้ากลายเป็นเรื่องที่ย้อนกลับได้**

เรื่องนี้ค้างมาหลายเดือนเพราะกลัวเลือกผิด · พอ build เป็น container มาตรฐาน การย้ายเจ้าคือเปลี่ยนปลายทางที่ push ไม่ใช่เขียนใหม่ · **ตัดสินใจผิดแล้วแก้ได้ในหนึ่งชั่วโมง แปลว่ามันไม่ใช่การตัดสินใจที่น่ากลัวอีกต่อไป** — รูปแบบเดียวกับที่ ADR 0031 ใช้หด "เลือก vendor อีเมล" ให้เหลือแค่แก้ hostname ใน `.env`

รองลงมาคือมันปิดช่องโหว่สองข้อที่ grill นี้เจอ: **ไม่มี `postinstall` และไม่มีสคริปต์ `prisma generate`** (ตอนนี้อาศัย `allowBuilds` ใน `pnpm-workspace.yaml` ให้ postinstall ของ `@prisma/client` รันเอง — host ที่ใช้ pnpm คนละเวอร์ชันหรือ `--ignore-scripts` จะได้ client เก่าเงียบ ๆ) และ **ไม่มี `engines` ล็อกเวอร์ชัน Node**

**ราคาที่จ่าย:** ต้องตั้ง `output: 'standalone'` · Dockerfile ของ Next มีขั้นตอนจุกจิก · และกับดักคลาสสิกของ Prisma คือ engine binary ผูกกับ libc ของ container (musl กับ glibc คนละไฟล์) ซึ่งพังตอน runtime ไม่ใช่ตอน build — ซึ่งเป็นเหตุผลเพิ่มอีกข้อที่ต้องคุม base image เอง

### Q4 — เป้าหมายคือ "ใช้ได้เกือบตลอด" ไม่ใช่ "ห้ามล่ม"

ข้อเท็จจริง 4 คือหลักฐาน: **Mise ไม่ใช่ POS ไม่มีใครยืนรอที่แคชเชียร์** ต่างจาก FoodStory/Wongnai ที่ล่มแล้วร้านคิดเงินไม่ได้ ของเราล่มแล้วร้านยังขายได้ตามปกติ

และระบบออกแบบมาให้กรอกย้อนหลังอยู่แล้ว — ledger เป็น append-only ทุกอย่างเป็นเอกสารที่บันทึกหลังเหตุการณ์ · ของมาส่งตอนเช้าแล้วเปิดระบบไม่ได้ ก็จดกระดาษแล้วมากรอกตอนบ่าย ซึ่ง**เป็นวิธีทำงานปกติ ไม่ใช่ workaround**

**ผลที่ตามมา:** instance เดียวพอ · ไม่ต้อง multi-region ไม่ต้อง load balancer · และเราไม่จ่ายค่า reliability ที่ยังไม่มีใครต้องการ

**วันที่จะเจ็บจริงคือวันสิ้นเดือน** ตอนเจ้าของร้านนั่งปิดตัวเลข — รับไว้อย่างรู้ตัว

### Q5 — Fly.io ภูมิภาค `sin`

| | region | always-on | deploy |
|---|---|---|---|
| **Fly.io** | `sin` | **~$3.3/เดือน** (512MB) · ~$5.9 (1GB) | CLI |
| Render | Singapore | ~$7 | เชื่อม repo |
| Cloud Run | asia-southeast1 | ~$10–15 | ต้องตั้ง gcloud + Artifact Registry |

Fly เป็นเจ้าเดียวในสามที่ **image ที่เราสร้างคือของที่มันรันตรง ๆ** ไม่มี buildpack แทรกกลาง ซึ่งเป็นเหตุผลเดียวกับ Q3 · `sin` เป็น region เดียวของ Fly ใน SEA

**ราคาที่จ่าย:** ต้องใช้ CLI ไม่ใช่คลิกหน้าเว็บ · Fly เคยล่มเป็นข่าวหลายรอบ และ support แพลนเล็กคือฟอรัมชุมชน — ซึ่ง Q4 บอกว่ารับได้ · egress $0.04/GB ในเอเชีย ซึ่งแอปที่ส่ง HTML กับ CSV แทบไม่ขยับ

**ปฏิเสธ Render:** แพงกว่าเท่าตัวเพื่อแลกกับ UI ที่ง่ายกว่า และ **free tier ของ Render หลับเมื่อไม่มีคนใช้** ซึ่งคือ scale-to-zero ที่ Q2 ปฏิเสธไปแล้ว

### Q6 — สคริปต์รัน manual SQL 19 ไฟล์ พร้อมเทสต์ที่แดงเมื่อมีไฟล์ตกหล่น

ข้อเท็จจริง 8 แปลว่าฐานข้อมูลใหม่จะได้ตารางจาก migration แต่**ไม่ได้ทั้ง 19 ไฟล์** ซึ่งไม่ใช่แค่ RLS แต่รวม **partial unique index ที่ Prisma เขียนไม่ได้** — เช่นกฎที่ ADR 0026 พึ่งอยู่ (`menu_pos_identity_unique` ที่ตั้งใจไม่มี `deleted_at` predicate) และกฎที่ทำให้ import ยอดขายวันเดิม *แทนที่* แทนที่จะซ้ำ · **พวกนี้พังเงียบ ไม่มี error ตอน deploy**

รูปแบบที่ใช้ไม่ใช่ของใหม่ — **โปรเจกต์นี้แก้ปัญหาเดียวกันมาแล้วที่ `tests/sweep-coverage.test.ts`** ซึ่งอ่าน dmmf แล้วแดงเมื่อมีตารางที่มี `tenantId` แต่ไม่อยู่ใน delete order · รอบนี้คือ `scripts/apply-manual-sql.ts` ถือลำดับไฟล์ + เทสต์ที่อ่าน `prisma/manual/*.sql` แล้วแดงถ้ามีไฟล์นอกลำดับ

รหัสผ่านของ `mise_app` อ่านจาก env (`MISE_APP_DB_PASSWORD`) **แทนที่จะให้คนแก้ไฟล์** ซึ่งแก้เรื่อง "รันซ้ำไม่ได้" ไปด้วย และปิดหนี้ "rotate รหัสทั้งสอง role" ที่ค้างจาก Part 30 · `CREATE ROLE` ต้องห่อด้วย `DO $$ ... $$` ที่เช็ค `pg_roles` เพราะ Postgres ไม่มี `CREATE ROLE IF NOT EXISTS`

**ปฏิเสธ:** ย้ายเข้า `prisma/migrations/` — `CLAUDE.md` ห้ามไว้ตรง ๆ และมีเหตุผล คือไฟล์พวกนี้จัดการ **ROLE** ซึ่ง migration ไม่ควรเป็นเจ้าของ
**ปฏิเสธ:** checklist ในเอกสาร — เรามีของแบบนั้นอยู่แล้วในรูป "⚠️ Still owed" ใน `CLAUDE.md` **และมันค้างมาสองสปรินต์** ซึ่งเป็นหลักฐานว่ารูปแบบนี้ไม่ทำงาน

### Q7 — rate limit ชั้น 2 นับในหน่วยความจำ 20 ครั้งต่อ IP ต่อชั่วโมง

ชั้น 1 (ADR 0031 Q6) เขียนไว้เองว่าไม่จับอะไร: **หมื่นที่อยู่ยิงคนละครั้ง** ไม่มี identifier ไหนเกินเพดาน

ปกติ "นับในหน่วยความจำ" คือของที่พังทันทีที่มีสองอินสแตนซ์ — **แต่ Q2 และ Q4 ตัดเงื่อนไขนั้นทิ้งไปแล้ว** อินสแตนซ์เดียวรันค้าง คือเงื่อนไขที่ทำให้มันถูกต้อง ไม่ใช่ hack

อ่าน IP จาก **`Fly-Client-IP`** ซึ่ง Fly proxy เป็นคนตั้งและไคลเอนต์ปลอมไม่ได้ (`X-Forwarded-For` ปลอมได้ ห้ามใช้) · ถ้าไม่มี header ให้ **ผ่าน** ไม่ใช่บล็อก เพื่อไม่ให้ dev พัง

**20 ครั้งต่อชั่วโมง** หลวมพอสำหรับพนักงาน 5–6 คนที่ใช้ Wi-Fi ร้านเดียวกันและกดพลาดคนละสองสามครั้ง แต่ตัดการยิงหมื่นที่อยู่ทิ้งทันที

**ปฏิเสธ:** ตารางใหม่ — ทุกครั้งที่มีคนกดปุ่มเราเขียนดิสก์ ซึ่งคือสิ่งที่ผู้โจมตีต้องการ · **การป้องกัน DoS ที่ตัวมันเองเป็นช่องให้ DoS**
**ปฏิเสธ:** Cloudflare หน้าบ้าน — dependency ใหม่ + DNS ซับซ้อนขึ้น เก็บไว้เป็นทางที่สองเมื่อมีหลายร้าน

**จุดอ่อนที่รับไว้อย่างรู้ตัว:** ตัวนับหายตอนรีสตาร์ท (แต่เราคุมเวลารีสตาร์ท ผู้โจมตีไม่ได้คุม) · และถ้าวันหนึ่งเพิ่มเป็นสองอินสแตนซ์มันจะรั่วเป็นสองเท่าเงียบ ๆ — **กันด้วยการให้มันส่งเสียงตอนสตาร์ท** ไม่ใช่ปล่อยให้ค่อย ๆ ผิด

### Q8 — Neon โปรเจกต์ใหม่ แพลนฟรี ยอมให้ compute หลับ

**โปรเจกต์ใหม่ ไม่ใช่ branch** — branch คัดลอกข้อมูลจากพ่อแม่ โปรดักชันจะได้เศษข้อมูลเทสต์ติดมา · และเรื่องรัศมีความเสียหายสำคัญกว่า: `db:reset --force` กับ `test:sweep` ที่เขียนว่า "Dev branch only" · **คนละ branch ในโปรเจกต์เดียวกัน = ชี้ผิดคือพิมพ์ผิดตัวเดียว · คนละโปรเจกต์ = ต้องไปเอา credential คนละชุดมาวางเอง ซึ่งเกิดโดยบังเอิญไม่ได้** · แพลนฟรีให้ 100 โปรเจกต์ การแยกจึงฟรี

**ยอมให้หลับ** แม้ว่ามันจะย้อนแย้งกับ Q2 ครึ่งหนึ่ง — เราเลือกแอปที่รันค้างเพื่อเลี่ยง cold start แต่ฐานข้อมูลยังหลับอยู่ดี และหน้าแรกของแต่ละครั้งจะช้า 1–3 วินาที · จ่าย Launch เพื่อปิด autosuspend ราว **$19/เดือน ซึ่งแพงกว่าเซิร์ฟเวอร์ทั้งตัวเกือบหกเท่า** เพื่อลบดีเลย์ที่ยังไม่มีร้านจริงบอกว่ารำคาญ — เหตุผลเดียวกับ Q4

⚠️ **ยังไม่ได้ตรวจ:** แพลนฟรีมีโควตาชั่วโมง compute ต่อเดือน ถ้าใช้หนักกว่าที่คิดอาจชนเพดาน ต้องดูของจริงหลัง deploy

### Q9 — `release_command` รัน `prisma migrate deploy` แล้วตามด้วยสคริปต์ manual SQL

Fly รัน `release_command` **ใน image ใหม่ ก่อนเวอร์ชันใหม่ขึ้นจริง** เข้าถึง secrets ได้ และ **ถ้า exit ไม่เป็นศูนย์ deploy ถูกยกเลิก** (timeout 5 นาที ปรับได้)

นี่คือสิ่งที่ทำให้ Q6 สมบูรณ์: เทสต์จับได้แค่ตอนเพิ่มไฟล์ใหม่ **มันไม่บังคับให้ใครรันสคริปต์** · พอมาอยู่ใน `release_command` **การลืมกลายเป็นสิ่งที่ทำไม่ได้เชิงโครงสร้าง** และถ้าพัง เวอร์ชันเก่ายังวิ่งอยู่ ร้านไม่เห็นอะไรผิดปกติ — ดีกว่ารันมือแล้วพัง ซึ่งได้โค้ดใหม่บนฐานข้อมูลเก่า

ทั้งสองคำสั่งใช้ `DIRECT_URL` (role `neondb_owner`) เพราะ `mise_app` สร้างตารางและ role ไม่ได้ · **แปลว่า credential ของ owner ต้องอยู่บน Fly ด้วย** — ใครเข้าถึงเครื่องได้ ได้ owner ไปด้วย รับไว้อย่างรู้ตัว

**ราคาที่จ่าย:** Prisma ไม่มี down migration และตอนนี้ migration จะขึ้นไป **โดยไม่มีใครกดยืนยัน** · รับได้เพราะการเปลี่ยนสคีมาเป็น 🛑 stop-and-ask ตั้งแต่ตอนเขียนโค้ดอยู่แล้ว และมี 27 migration ใน 7 สปรินต์ = ไม่ถึงเดือนละครั้ง

### Q10 — แยกเป็นสองหมุด และเล็งหมุด A ก่อน

ลำดับที่ถือกันมาตั้งแต่ handoff คือ *เลือก host → rate limit → ซื้อโดเมน → deploy* · **แต่ Fly แจก `<ชื่อแอป>.fly.dev` พร้อม TLS ให้ฟรี** `AUTH_URL` ชี้ไปที่นั่นได้ทันที

> **หมุด A — Kong ใช้ Mise จริงจากมือถือได้** · ไม่ต้องมีโดเมน เพราะ Resend ส่งถึงเจ้าของบัญชีได้อยู่แล้ว และเจ้าของบัญชีคือ Kong
>
> **หมุด B — พนักงานร้านทดลองเข้าระบบได้** · ต้องมีโดเมน + verify SPF/DKIM เพราะ **วันนี้ Resend ส่งได้เฉพาะอีเมลเจ้าของบัญชี** — พาร้านมานั่งดูแล้วให้เขาลองล็อกอิน ลิงก์จะไม่มีวันไปถึง

**หมุด A จบได้ในวันเดียว ไม่ต้องรออะไรจากโลกภายนอก** ส่วนหมุด B มีเวลารอที่เร่งไม่ได้ (ซื้อโดเมน · DNS propagate · verify DKIM) · มัดรวมกันแปลว่ารอโดเมนโดยไม่จำเป็น ทั้งที่ระหว่างนั้นควรได้ใช้ระบบจริงบนมือถือแล้ว **และการได้ใช้จริงคือที่ที่จะเจอปัญหาที่ localhost ไม่มีวันแสดง**

การแยกแบบนี้คือรูปแบบเดียวกับที่ ADR 0031 ใช้ปลด blocker ที่ค้างสามสปรินต์ — แยก "ส่งอีเมลได้จริง" ออกจาก "มี URL จริง"

**ราคาที่จ่าย:** พอย้ายไปโดเมนจริง ลิงก์ล็อกอินเก่าจะพังและ session อาจหลุด — แต่ตอนนั้นมีผู้ใช้คนเดียว ซึ่งเป็นเวลาที่ถูกที่สุดที่จะเปลี่ยน

### Q11 — ยอมรับประวัติ 6 ชั่วโมงที่หมุด A และผูก `pg_dump` อัตโนมัติไว้กับหมุด B

ข้อมูลของ Mise เกือบทั้งหมดพิมพ์ด้วยมือและไม่มีต้นทางให้ดึงกลับ · มีแค่ยอดขายที่ดึงกลับได้จากไฟล์ POS

แต่ความเสี่ยงจริงแคบกว่าที่ตัวเลขทำให้รู้สึก: **ledger เป็น append-only ไม่มีเส้นทาง UPDATE หรือ DELETE สำหรับ movement เลย** เอกสารถูก void ไม่ใช่ถูกลบ — **"มีคนเผลอลบข้อมูล" ไม่ใช่โหมดพังที่มีอยู่จริงในระบบนี้** · โหมดที่มีจริงคือบั๊กเขียนผิด (แก้ด้วย void) · Neon ทำข้อมูลหาย (แทบเป็นไปไม่ได้) · และคนรัน `db:reset` ใส่โปรดักชัน ซึ่ง Q8 ลดไปแล้ว

**หมุด A ไม่มีข้อมูลจริงสักแถว** การจ่ายค่าสำรองข้อมูลที่ยังไม่มีคือการซื้อของที่ยังไม่มีใครต้องการ · แต่ **ก่อนร้านจริงพิมพ์ข้อมูลแถวแรก ต้องมี GitHub Action ตั้งเวลา `pg_dump` เก็บเป็น artifact** — ไม่มี vendor ใหม่ ไม่มีค่าที่เก็บ เก็บ 90 วัน และทำงานเองไม่ใช่สิ่งที่ต้องจำ

ผูกไว้กับ**หมุดที่มีชื่อ** ไม่ใช่คำว่า "ไว้ทีหลัง" ด้วยเหตุผลเดียวกับ Q6

**ปฏิเสธ:** Neon Launch เพื่อได้ 7 วัน — แก้แค่ครึ่งเดียว (7 วันก็หายถ้าไม่มีใครสังเกต) และแพงกว่าเซิร์ฟเวอร์ทั้งตัว · `pg_dump` ที่เก็บ 90 วันให้มากกว่าในราคาศูนย์

### Q12 — `error.tsx` · `not-found.tsx` · `loading.tsx` ที่หมุด A · error tracking ที่หมุด B

ข้อเท็จจริง 9 แปลว่าบนโปรดักชัน คนใช้จะเจอหน้า error มาตรฐานของ Next **เป็นภาษาอังกฤษ** พร้อมรหัส digest ไม่มีทางกลับ · และ **localhost ไม่มีวันแสดงให้เห็น เพราะ dev โชว์ stack trace** — กับดักแบบเดียวกับที่ ADR 0031 เจอตอนเปิดการส่งอีเมลจริง

🔴 **และมันย้อนกลับมาที่ Q8**: ตอนตกลงให้ Neon หลับ เหตุผลรองรับคือ "จะให้หน้าจอบอกว่ากำลังโหลด" — **แต่ไม่มี `loading.tsx` สักไฟล์ คำสัญญานั้นจึงยังไม่มีของรองรับ** หน้าแรกของแต่ละครั้งจะค้างขาว 1–3 วินาทีเงียบ ๆ · สามไฟล์นี้จึงไม่ใช่งานเสริม มันคือเงื่อนไขที่ทำให้ Q8 เป็นการตัดสินใจที่ยอมรับได้

**error tracking ยกไปหมุด B** — Sentry เป็น dependency ใหม่ = 🛑 stop-and-ask และยังไม่คุ้มตอนมีผู้ใช้คนเดียว · **จุดอ่อนที่บันทึกไว้:** `fly logs` ดูได้แค่ของสด ร้านเจอปัญหาตอนเช้าแล้วบอกตอนเย็น log อาจหายแล้ว

### Q13 — เครื่อง 1GB และ health check แค่ระดับ TCP

**1GB ไม่ใช่ 512MB** ต่างกันเดือนละ ~$2.6 · Prisma query engine เป็นโปรเซสแยกที่กินหน่วยความจำทับกับ Next server · **อาการของ OOM คือเครื่องถูกฆ่าแล้วรีสตาร์ทเงียบ ๆ ซึ่งหน้าตาเหมือน "แอปพังสุ่ม ๆ"** เราจะไล่หาบั๊กที่ไม่มีอยู่จริง และมันจะเกิดตอนมีคนใช้พร้อมกันหลายคน ซึ่งคือตอนพาร้านมานั่งดูพอดี

🔴 **health check ห้ามแตะฐานข้อมูล** Fly เช็คทุก 10–30 วินาที ถ้าทุกครั้งคิวรี Neon **compute จะไม่มีวันหลับ** = เผาโควตาแพลนฟรีตลอด 24 ชั่วโมงทั้งที่ร้านใช้วันละไม่กี่ครั้ง — **มันจะทำลาย Q8 เงียบ ๆ** · TCP check ตอบคำถามที่เราต้องการพอดี คือ "โปรเซสยังอยู่ไหม" · ส่วน "ฐานข้อมูลยังดีไหม" ไม่ใช่เรื่องที่ health check ควรตอบ เพราะถ้า Neon ล่ม การรีสตาร์ทแอปไม่ช่วยอะไร มันจะกลายเป็นวงจรรีสตาร์ทไม่รู้จบที่ทำให้แย่ลง

## Consequences

1. **การเลือกเจ้าถูกออกแบบให้ย้อนกลับได้ และนั่นคือคุณค่าหลักของ ADR นี้** ไม่ใช่การเลือก Fly · ถ้า Fly ไม่เวิร์ก การย้ายคือเปลี่ยนปลายทางที่ push

2. **Q2 กับ Q4 ทำให้ Q7 ถูกต้อง** — การตัดสินใจก่อนหน้าตัดเงื่อนไขที่จะทำให้ in-memory counter เป็น hack ทิ้งไป · แต่แปลว่า **ถ้าวันหนึ่งเพิ่มอินสแตนซ์ rate limit จะรั่วเป็นสองเท่า** และนั่นคือเหตุผลที่มันต้องส่งเสียงตอนสตาร์ท

3. **Q6 + Q9 รวมกันแก้ปัญหาที่ค้างสองสปรินต์** สคริปต์อย่างเดียวยังต้องมีคนรัน · `release_command` อย่างเดียวยังต้องมีคนบำรุงรายชื่อไฟล์ · สองอย่างคู่กันทำให้ลืมไม่ได้

4. **credential ของ `neondb_owner` จะอยู่บนเครื่องโปรดักชัน** เพราะ migration ต้องใช้ · นี่คือการขยายพื้นที่เสี่ยงที่รับไว้อย่างรู้ตัว ไม่ใช่ของที่มองข้าม

5. **`.fly.dev` เป็นที่อยู่ชั่วคราวโดยตั้งใจ** และการย้ายไปโดเมนจริงจะทำให้ลิงก์เก่าพัง — ต้องทำตอนที่ยังมีผู้ใช้คนเดียว

6. **`docker-compose.yml` ตายแล้ว** — เป็น Postgres local ที่ทิ้งไปตั้งแต่ Sprint 0 (บทเรียนข้อ 2 ใน CLAUDE.md) ไม่มีอะไรอ้างถึง · เก็บกวาดได้ตอนใส่ Dockerfile จริง

7. **ยังไม่ได้ตรวจสองข้อ และบันทึกไว้แทนที่จะเงียบ** — โควตาชั่วโมง compute ของ Neon แพลนฟรี · และพฤติกรรมจริงของหน่วยความจำบน 1GB ภายใต้การใช้งานจริง ทั้งสองต้องวัดหลัง deploy ไม่ใช่เดาตอนนี้
