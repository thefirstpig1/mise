# ADR 0028 — มื้อพนักงาน: สองตัวเลขที่ไม่เท่ากัน และคนที่ระบบยังไม่รู้จัก

**Status:** accepted · **Date:** 2026-08-28 · **Grill:** Q1–Q9
**Part:** Sprint 5 Part 26 · **Splits off from** ADR 0025 Q1 · **Uses** `MovementType.CONSUMPTION` (ADR 0022) · **Upholds** ADR 0021 Q10 (`menu.sale_price` stays refused) · **Fixes** a live defect in `stock-cost.ts` that Part 22 left one source type away from daylight.

## Context

มื้อพนักงานถูกกันไว้ตั้งแต่ Part 17 และถูกอ้างถึงใน schema comment ถึงสามที่ ก่อน Part นี้จะมีอยู่จริง สิ่งที่ grill พบคือ **โค้ดตัดสินไปแล้วมากกว่าที่แผนคิด และมีเรื่องหนึ่งที่กำลังผิดอยู่ตอนนี้**

เก้าข้อที่ยืนยันจากการอ่านโค้ดระหว่าง grill

1. **`MovementType.CONSUMPTION` ถูกออกแบบมารองรับ Part นี้ตั้งแต่ต้น.** `schema.prisma:585-591` เขียนไว้ตรง ๆ ว่า *"a sale and (later) a staff meal share the type and are told apart by `source_type`"* — ไม่มี movement type ใหม่ใน Part นี้ และ `stock_movement_sign_check` ไม่ถูกแตะ แบบเดียวกับ `WASTE_LOG` (ADR 0017 Q1)

2. **`SourceType.SALES_CONSUMPTION` ถูกตั้งชื่อเฉพาะเจาะจงแทนที่จะเป็นชื่อกลาง ๆ เพื่อ Part นี้โดยตรง.** `schema.prisma:2632-2637`: *"Named for the sale rather than generically, because a staff meal brings its own document and its own value here — a generic `origin` column would hold one value for a whole Part."*

3. **`WasteReason` ปฏิเสธ `STAFF_MEAL` ไว้แล้วโดยตั้งใจ** พร้อมเหตุผลว่า *"a staff meal is not waste. It is a sale that collected no money"* — เส้นแบ่งนี้ถูกขีดไว้ก่อน Part นี้ และ Part นี้ไม่ได้ย้ายมัน

4. **หมวดบัญชีสำหรับ "ซื้ออาหารพนักงานแยก" มีอยู่แล้ว.** `category` เป็น 3 ชั้น `account (COGS/OpEx) → accounting_section → group` (`validations/category.ts:23`) และ `tenant-init.ts:117` seed `OpEx / Labor / Salary` ไว้แล้ว ร้านสร้าง `OpEx / Labor / อาหารพนักงาน` เองได้วันนี้ เงินไปโผล่ที่ `opexSpend` ไม่ใช่ `cogsSpend`

5. **Mise ไม่มีโมเดลพนักงาน.** มีแต่ `User` (บัญชี login) กับ `TenantMembership` (`schema.prisma:257`) และเอกสารสี่ใบใช้ pattern เดียวกัน — FK ไปที่ login ที่บันทึก **บวกชื่อ free text** ของคนที่ทำจริง (`countedByName:912`, `wastedByName:1528`, `dispatchedByName:1677`, `receivedByName:1695`) เหตุผลอยู่ที่ `schema.prisma:1524-1526`: ในร้าน SME ไทยเจ้าของถือบัญชีเดียว พนักงานเป็นคนทำงาน FK อย่างเดียวจะบันทึกว่า *เจ้าของทิ้งของทุกชิ้น* — เรียบร้อยแต่โกหก

6. **ไม่มี "ราคาเมนู" ในระบบ.** `menu.sale_price` ถูกปฏิเสธโดย ADR 0021 Q10 (`schema.prisma:2499`) มีแต่ `recipe.plannedPrice` ซึ่งเป็น **ราคาที่ตั้งใจ** บนแบบร่างเท่านั้น ราคาที่ขายได้จริงคำนวณจาก `sum(netAmount)/sum(qty)` (`menu-lab-read.ts:158`) และ `netAmount` เป็นราคา **หลังส่วนลด ไม่รวม VAT ไม่รวม service charge** (ADR 0019 Q10)

7. **`sales_line` เก็บ *ยอด* ส่วนลด แต่ไม่เก็บ *เหตุผล*.** มี `discountAmount` (`schema.prisma:2339`) ไม่มีช่องสำหรับ tag ที่ POS ติดมา ส่วน `sales_import_profile.columnMap` เป็น JSONB — *"Data, not code"* (`schema.prisma:1957`) — เพิ่ม key ใหม่ได้โดยไม่ต้อง migrate แต่ไม่มีที่ให้ลง

8. **ร้านที่ POS ตีมื้อพนักงานเป็นส่วนลด 100% กำลังถูกตัดสต๊อกอยู่แล้ววันนี้.** `menuSalesForDay` (`consumption.ts:135`) group ตาม `menuId` แล้วรวม `qty` โดยไม่สนใจว่า `netAmount` เป็น 0 → Part 22 โพสต์ `CONSUMPTION` ให้เรียบร้อย **การตัดสต๊อกถูกต้อง** (ของออกจากชั้นจริง) แต่มันไปนอนใน `cogsSold` ซึ่งเป็นต้นทุนขาย ไม่ใช่สวัสดิการ

9. **`consumptionMoves` ถูกเก็บด้วย movement type แต่ถูกอ่านต่อด้วย source type — สอง filter คนละชั้น.** `fifo-replay.ts:532,574` push ทุก `CONSUMPTION`/`CONSUMPTION_REVERSAL` โดยไม่ดู source เลย ขณะที่ `stock-cost.ts:273` ค้น `reversalOfItemId` เฉพาะ `sourceType === "SALES_CONSUMPTION"` และ `stock-cost.ts:741` ค้น run จาก `salesConsumptionItem` เท่านั้น ช่องว่างนี้ไม่มีผลตราบใดที่ `CONSUMPTION` มี source เดียว — Part นี้เป็นตัวที่สอง

## Decision

### Q1 — โลกจริงมีสามแบบ มีสองแบบเท่านั้นที่เป็นคำถามเรื่องสต๊อก

ร้านทำมื้อพนักงานสามแบบ: (1) พนักงานสั่งเมนูที่ขายอยู่ · (2) ตั้งงบรายเดือนแล้วซื้อของแยก · (3) คนครัวหยิบของในร้านมาทำกินกัน

**แบบ 2 ไม่ใช่เรื่องของ Part นี้ และไม่ต้องเขียนโค้ดใหม่เลย** ของไม่เคยเข้าสต๊อกร้าน ผู้จัดการซื้อมากินเลย มันคือ [Expense] ธรรมดาใต้หมวด `OpEx / Labor` (Context 4) หน้าที่ของเราคือ **ชี้ทางไปหน้ารายจ่าย** ไม่ใช่สร้างของใหม่มารองรับ

**สิ่งที่ Part 26 ครอบคลุมคือแบบ 1 กับ 3 — สองกรณีที่ของออกจากชั้นวางของร้าน**

**`staff_meal_mode` ถูกปฏิเสธ.** grill เริ่มจากสมมติฐานว่าต้องมี tenant setting ให้ร้านเลือกโหมด แต่พอเอกสารมีรูปร่างแล้ว แบบ 1 กับ 3 ต่างกันแค่ว่ามี `menuId` หรือไม่มี เอกสารเดียวรองรับทั้งคู่โดยธรรมชาติ ไม่มีอะไรให้ตั้งค่า — setting ที่ถูกขอไว้ละลายไปเพราะโครงสร้างตอบมันไปแล้ว

### Q2 — สองตัวเลข ไม่ใช่หนึ่ง และ ledger ไม่มีสิทธิ์เลือก

มื้อพนักงานหนึ่งมื้อมีตัวเลขสองตัวที่ **ไม่เท่ากันและไม่แทนกัน**:

| | ราคาขาย ฿89 | ต้นทุนวัตถุดิบ ฿32 |
|---|---|---|
| ตอบคำถาม | พนักงานใช้สิทธิ์ไปเท่าไหร่ | ร้านเสียของไปเท่าไหร่ |
| เป็นตัวเลขของ | การคุมงบ/สวัสดิการ | บัญชี |

**Ledger เคลื่อนที่ต้นทุนวัตถุดิบเสมอ ไม่มี setting.** ADR 0014 บอกว่าต้นทุนไม่ถูกเก็บที่ไหนเลย มันเกิดจาก FIFO replay ตอนอ่าน กะเพราหมูหนึ่งจานที่ออกจากสต๊อกคือหมู 80 ก. + ข้าว 200 ก. + ไข่ 1 ฟอง และ FIFO เป็นคนบอกว่าสามอย่างนั้นรวมกันเท่าไหร่ จะสั่งให้เป็น ฿89 ไม่ได้ เพราะ ฿89 กระจายลงหมู/ข้าว/ไข่อย่างมีความหมายไม่ได้

**และการลงบัญชีที่ราคาขายจะสร้างค่าใช้จ่ายผี ฿57 ที่ไม่มีเงินออกจากร้านคู่กัน** ราคาขายจึงอยู่บนเอกสารในฐานะ **ตัวเลขคุม** ไม่ใช่ต้นทุน

### Q3 — โควตาต้องนับต่อคน ดังนั้นระบบต้องรู้จักคน

ความโปร่งใสที่ขอไว้คือ *"รู้ว่าใครสั่งเกิน"* และ free text นับไม่ได้ — `"สมชาย"` กับ `"สมชาย "` กับ `"ชาย"` คือสามคน **`staff_member` จึงเกิดขึ้น** เป็นรายชื่อของตัวเอง

**ไม่เชื่อมกับ `User`.** `User` ตอบว่า *ใครล็อกอินได้*, `staff_member` ตอบว่า *ใครกิน* — คนละคำถาม การใส่ `userId` แบบ nullable ไว้ให้เจ้าของที่มี login จะสร้างคำถามใหม่ทันทีว่า *ชื่อไหนชนะ* ซึ่งไม่มีใครถาม เจ้าของกินมื้อพนักงานก็เป็นแถวหนึ่งในรายชื่อเหมือนคนอื่น วินัยเดียวกับ ADR 0027: **identity ไม่ใช่ lifecycle** และที่นี่ **บัญชีไม่ใช่คน**

### Q4 — สามเส้นรอบ `staff_member` ที่กันไม่ให้ Part นี้กลายเป็นระบบ HR

**เส้นที่ 1 — ไม่ไปแทนที่ช่อง free text อีกสี่ช่อง.** `wastedByName` / `countedByName` / `dispatchedByName` / `receivedByName` ยังเป็น free text ต่อไป มีแค่เอกสารมื้อพนักงานที่ชี้หา `staff_member` การแปลงสี่ช่องนั้นเป็น Part ของตัวเอง (ต้อง migrate ข้อมูลเก่า + ต้องตอบว่าชื่อที่จับคู่ไม่ได้จะเป็นอะไร) ถ้ารวบตอนนี้ Part 26 จะกลายเป็น Part ระบบพนักงาน แล้วเรื่องมื้ออาหารจะกลายเป็นของแถม

**เส้นที่ 2 — เก็บแค่ `name` · `branchId` · `isActive` · `deletedAt`.** ไม่เอาเลขบัตรประชาชน เงินเดือน เบอร์โทร วันเริ่มงาน ตำแหน่ง ชื่อพนักงานเป็นข้อมูลส่วนบุคคลตาม PDPA ยิ่งเก็บมากยิ่งรับผิดชอบมาก และไม่มีคำถามไหนใน Part 26 ที่ห้าตัวนั้นตอบได้

**เส้นที่ 3 — `staffMemberId` เป็น nullable.** แบบ 1 มีคนแน่นอนและ **ต้องระบุ** ไม่งั้นโควตาทำงานไม่ได้ แบบ 3 (คนครัวทำหม้อใหญ่) **ไม่มีคนเดียว** จะบังคับให้ระบุคือบังคับให้โกหก กฎ "ต้องระบุ" จึงอยู่ที่ชั้น application เฉพาะเอกสารที่มี `menuId` — ไม่ใช่ `NOT NULL` ที่ฐานข้อมูล เพราะมีเคสที่ว่างโดยชอบธรรม

**พนักงานที่ลาออกยังถูกนับเต็มในรายงานย้อนหลัง พร้อมป้ายว่าลาออกแล้ว** กฎเดียวกับ ADR 0027 Q5 เป๊ะ: `isActive` เป็นคำกล่าวเกี่ยวกับอนาคต ไม่แตะอดีต ถ้าตัดคนที่ลาออกออกจากรายงาน การกดปุ่มวันนี้จะเปลี่ยนตัวเลขของเดือนที่แล้ว

### Q5 — ทางเข้ามีทางเดียว: พิมพ์เอง

**เหตุผลที่ชี้ขาดคือไฟล์ POS ไม่มีชื่อคน** ไฟล์บอกได้แค่ *"กะเพราหมู 1 จาน ส่วนลด 100%"* ไม่เคยบอกว่า *"สมชาย"* ต่อให้ดึงจาก POS ได้สมบูรณ์แบบ สิ่งเดียวที่ Q3 ซื้อ `staff_member` มาเพื่อตอบก็ยังต้องพิมพ์อยู่ดี

บวกอีกสอง: แบบ 3 ไม่มีบิลใน POS ตั้งแต่ต้น · และการดึงจาก POS ต้องแก้ `sales_line` + แก้ import ซึ่งเป็น code path ที่ป้องกันแน่นที่สุดในระบบ (header fingerprint, REPLACE ทั้งวัน) เพื่อแลกกับข้อมูลที่ยังตอบคำถามหลักไม่ได้

หน้าจอเป็นแบบเดียวกับ `/waste`: เหตุการณ์เดียว บันทึกทันที ไม่มี draft

### Q6 — อ่าน tag ส่วนลดมาแสดง แต่ไม่ตัดสินใจแทน

Context 8 แปลว่า **ถ้า Part 26 ให้ร้านที่ POS ตัดไปแล้วพิมพ์ซ้ำ สต๊อกจะถูกตัดสองรอบ** โดยไม่มีอะไรบนหน้าจอผิดปกติ — ความล้มเหลวแบบที่แย่ที่สุด

คำเตือนแบบ `net = 0` ทื่อเกินไป เพราะมันรวม **ของแถม · voucher · บิลยกเลิก · มื้อพนักงาน** ไว้ในกองเดียว ซึ่งไม่ช่วยใครตัดสินใจ POS ส่วนใหญ่ติด tag บอกว่าลดเพราะอะไร

**ตัดสินใจ: import tag เป็นข้อความดิบลง `sales_line.discount_reason` แล้วเอามาแสดงให้คนอ่าน — ระบบไม่ map ไม่ตีความ ไม่ย้ายเงิน**

คำเตือนกลายเป็น *"วันนี้มี 3 รายการส่วนลด: 'พนง.' ×2, 'ของแถม' ×1 — ถ้า 'พนง.' คือมื้อพนักงาน POS ตัดสต๊อกให้แล้ว บันทึกซ้ำจะตัดสองรอบ"* **เตือน ไม่บล็อก** — pattern เดียวกับ Part 20a ที่เตือนเรื่องไฟล์ไม่ครบวัน

**สิ่งที่ถูกปฏิเสธคือขั้นถัดไป: ให้ร้าน map tag แล้วย้ายบรรทัดพวกนั้นออกจาก `cogsSold`** สองเหตุผล — (ก) มันทำให้ตัวเลขในบัญชีขึ้นกับข้อความที่ร้านพิมพ์เองในสเปรดชีต ขณะที่ ADR 0019 Q7 ใช้ทั้ง Part ตัดสินว่า *POS code คือ identity ชื่อได้แค่แนะนำ ห้ามตัดสิน* · (ข) มันมีคำถามที่ยังไม่มีคำตอบ: ร้าน map tag วันนี้แล้วเดือนที่แล้วที่โพสต์ไปแล้วย้ายด้วยไหม ถ้าย้าย = เปอร์เซ็นต์ต้นทุนอาหารเดือนที่แล้วขยับเพราะกดปุ่มวันนี้ ซึ่ง ADR 0027 Q5 ปฏิเสธไปแล้ว **นั่นคือ Part ของตัวเอง**

### Q7 — ราคามาจากยอดขายจริง และถูก freeze ลงเอกสาร

Context 6 แปลว่าไม่มีราคาเมนูให้หยิบ **ราคาที่ใช้คุมโควตาจึงคำนวณจากยอดขายจริง** ตามกฎที่ ADR 0025 Q2 ตัดสินไปแล้วว่า *พอเมนูขายแล้ว ราคาที่ขายได้คือราคา* — `menu.sale_price` ยังถูกปฏิเสธอยู่ Part นี้ไม่เปิดมันกลับมา

**freeze ลงเอกสารตอนบันทึก** เพราะมันเป็นค่าที่คำนวณสด ๆ และขยับตลอด ถ้าไม่ freeze การเช็คโควตาของเดือนที่แล้วจะเปลี่ยนคำตอบเองเมื่อเวลาผ่านไป — วินัยเดียวกับที่ `sales_consumption_run` freeze `cancelled_sale_policy` (ADR 0022 Q4)

**ลำดับ:** ราคาที่ขายได้จริง → ถ้าเมนูยังไม่เคยขาย ใช้ `recipe.plannedPrice` **พร้อมป้ายว่า "ราคาที่ตั้งใจ"** → ถ้าไม่มีอีก **`null` ไม่ใช่ ฿0** และโควตาบอกตรง ๆ ว่ายังเช็คให้ไม่ได้ (กฎ ADR 0019: null แปลว่ายังวัดไม่ได้ ไม่เคยแปลว่าศูนย์) เอกสารเก็บด้วยว่าราคามาจากแหล่งไหน เพราะตัวเลขที่บอกที่มาตัวเองไม่ได้ อธิบายตัวเองไม่ได้

**ราคานี้ไม่รวม VAT และไม่รวม service charge** กะเพราป้ายราคา ฿89 จะออกมา ฿83.18 พนักงานกับผู้จัดการคิดเป็นราคาป้าย ระบบคิดเป็นราคา net — **ต้องเขียนบนหน้าจอ** ไม่ใช่ปล่อยให้เดา

### Q8 — สองตาราง และ item คือ source ของ ledger

ไม่ใช่เรื่องรสนิยม แบบ 1 บังคับมัน: กะเพราหมู 1 จานระเบิดเป็น 3 movements แต่ `stock_movement_source_unique` เป็น key บน**คู่** `(source_type, source_id)` แถวเดียวเป็น source ของ 3 movements ไม่ได้ และทริค "สามค่าบนหนึ่ง id" ของ ADR 0018 Q4 ยืดไม่ถึง N ที่ไม่จำกัด — ข้อสรุปเดียวกับ ADR 0022 Q1 ทุกประการ

| ตาราง | ถืออะไร |
|---|---|
| `staff_meal` | เหตุการณ์: branch · `businessDate` (`@db.Date` ตามกฎ P15) · `staffMemberId?` · `menuId?` · จำนวนที่ · ราคาที่ freeze + แหล่งที่มา · `recordedBy` + `recordedByName` · void |
| `staff_meal_item` | `productId` · `qty` **signed, base unit** · `inputQty?`/`inputUnitId?` (เฉพาะบรรทัดพิมพ์มือ) · `reversalOfItemId?` — **แถวนี้คือ source ของ ledger** |

- แบบ 1: `menuId` มี → items เกิดจากการระเบิดสูตร **ณ วันนั้น** (ADR 0021 Q4)
- แบบ 3: `menuId` null → items พิมพ์มือ พร้อมหน่วยที่พิมพ์ แบบ `waste_log`

**ไม่รวมยอดต่อวัน** ต่างจาก ADR 0022 Q1 ที่รวมเพราะหนึ่งวันมี sales line เป็นพันและการไม่รวมจะทำให้ ledger บวม ~50 เท่า ที่นี่วันละ ~10 แถว การรวมจะทำลายการแยกรายคน ซึ่งคือทั้งหมดของ Q3 เพื่อแลกกับการประหยัดที่ไม่มีอยู่จริง

**การยกเลิกคือการ append** — reversal items เข้าเอกสารเดิม + stamp `voidedAt` โพสต์ `CONSUMPTION_REVERSAL` แบบเดียวกับ `sales_consumption_item` และ `waste_log` ไม่มีการแก้ในที่ ไม่มี delete

### Q9 — ตัวเลขที่ใช้คุม อยู่ที่ไหน และตัวไหนไม่ต้องมี

- **เพดานราคาต่อจาน** → `tenant.staff_meal_max_menu_price` (nullable, null = ไม่คุม) เป็นนโยบายของธุรกิจ ตามแบบ `tenant.cancelled_sale_policy` และ `tenant.gross_profit_method`
- **โควตาต่อคนต่อวัน** → `tenant.staff_meal_daily_quota` เป็นค่าตั้งต้น + `staff_member.daily_quota_amount` (nullable) ไว้ override รายคน เพราะร้านส่วนใหญ่ให้เท่ากันหมด แต่มีเสมอที่หัวหน้าครัวได้มากกว่า ถ้าไม่มี override ร้านจะต้องปิดโควตาทั้งร้านเพราะคนเดียว

**งบต่อสาขาต่อเดือนถูกปฏิเสธ** ตอนที่มันถูกพูดถึง มันกำลังอธิบาย**แบบ 2** ซึ่งเป็นเรื่องของหน้ารายจ่าย ไม่ใช่เรื่องสต๊อก สำหรับแบบ 1 กับ 3 หน้าจอแสดง *"เดือนนี้ใช้ไป ฿4,200"* ได้อยู่แล้วโดยไม่ต้องมีตัวเลขงบเก็บไว้เทียบ การเพิ่มคอลัมน์งบตอนนี้คือการเพิ่มของที่ไม่มีคำถามไหนเรียกร้อง — วินัยเดียวกับที่ ADR 0027 ปฏิเสธ `deactivated_at` แล้วจบ Part ได้โดยไม่มี migration เลย **และวันที่ร้านขอจริง คำถามจะชัดกว่าตอนนี้ว่างบเป็นราคาขายหรือราคาทุน**

## Consequences

1. **มีบั๊กจริงที่ Part นี้ต้องแก้ ไม่ใช่ของใหม่ที่ Part นี้สร้าง.** Context 9: `stock-cost.ts:273` ค้น `reversalOfItemId` เฉพาะ `sourceType === "SALES_CONSUMPTION"` พอ `STAFF_MEAL` โผล่มาเป็น `CONSUMPTION` มันจะได้ `null` → **การยกเลิกจะคืนของที่ราคาล่าสุด แทนที่จะคืนที่ราคาที่มันออกไป** ซึ่งคือสิ่งที่ ADR 0022 Q6 สร้าง `CONSUMPTION_REVERSAL` ขึ้นมาป้องกันโดยเฉพาะ ยกเลิกสองรอบแล้วมูลค่าสต๊อกเปลี่ยนโดยไม่มีอะไรเกิดขึ้นจริง **ต้องแก้ก่อนโพสต์มื้อพนักงานตัวแรก**

2. **การที่มื้อพนักงานหลุดจาก `cogsSold` ถูกโดยบังเอิญ และต้องกลายเป็นกฎที่ตั้งใจ.** `stock-cost.ts:741` ค้น run จาก `salesConsumptionItem` ด้วย id ของ item มื้อพนักงาน → หาไม่เจอ → `continue` คำตอบถูก (มื้อพนักงานเป็นสวัสดิการ ไม่ใช่ต้นทุนขาย) แต่ถูกเพราะ query หาไม่เจอ ไม่ใช่เพราะมีใครเขียนกฎไว้ **เปลี่ยนเป็น filter บน source type ที่ตั้งใจ พร้อม test ที่ปักไว้** — วันที่มีคนขยาย query นั้น มันจะพังเงียบ ๆ

3. **วิธี "นับสต๊อก" แยกมื้อพนักงานออกจาก COGS ไม่ได้เลย และต้องบอกผู้ใช้.** `opening + purchases − closing` ไม่รู้จักเหตุผล มื้อพนักงานทำให้สต๊อกปลายงวดลด → ต้นทุนขายสูงขึ้นโดยอัตโนมัติ ร้านที่ใช้วิธีนี้จะเห็นมื้อพนักงานปนอยู่ใน COGS เสมอ ข้อ 2 เป็นจริงเฉพาะวิธี **สูตรอาหาร** — เขียนบนหน้าจอ ไม่ใช่ปล่อยให้เข้าใจผิด

4. **คำเตือนเรื่องตัดซ้ำเป็นการป้องกันชั้นเดียว และไม่บล็อก.** ร้านที่ POS ตัดไปแล้วยังพิมพ์ซ้ำได้ถ้ายืนยัน นี่เป็นการแลกโดยตั้งใจ — บล็อกจริงต้องรู้ว่า tag ไหนแปลว่าอะไร ซึ่ง Q6 ปฏิเสธไปแล้ว

5. **`sales_line.discount_reason` เกิดมาเป็นข้อความดิบที่ไม่มีใคร map.** วันที่มีคนอยากให้มัน map แล้วย้ายเงิน ต้องอ่าน Q6 และ ADR 0019 Q7 **ก่อน** เขียนโค้ด นี่คือหนี้แบบเดียวกับที่ ADR 0026 ทิ้ง `menu_alias` ไว้ให้ Part 27 เจอ

6. **`staff_member` จะดึงช่อง free text อีกสี่ช่อง.** Q4 เส้นที่ 1 กันไว้ใน Part นี้ แต่แรงดึงจะไม่หายไป Part ที่รับเรื่องนั้นควรเปิดคำถามใหม่ ไม่ใช่ค่อย ๆ เพิ่ม FK ทีละใบเงียบ ๆ

7. **`TENANT_SCOPED_DELETE_ORDER` ต้องรับสามตารางใหม่ ลูกก่อนแม่** (`tests/support/sweep.ts`) ไม่งั้น `sweep-coverage.test.ts` แดง — ซึ่งคือหน้าที่ของมัน

8. **ไม่มี movement type ใหม่ และ `stock_movement_sign_check` ไม่ถูกแตะ** การเต้นสองจังหวะของ ADR 0013 ไม่ใช้กับ Part นี้ แบบเดียวกับ `WASTE_LOG` และ `STOCK_COUNT`
