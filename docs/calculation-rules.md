# ทะเบียนกฎการคำนวณ (Calculation Rules Register)

> **หน้านี้มีไว้ทำอะไร** — รวมกฎการคำนวณ/การตีมูลค่าทุกข้อของ Mise ไว้ที่เดียว เพื่อให้ตอบสองคำถามนี้ได้ตอนจบโปรเจกต์:
> 1. **มีกฎไหนขัดกันเองไหม** — กฎสองข้อที่ตัดสินคนละ Sprint แล้วให้ตัวเลขคนละแบบกับเหตุการณ์เดียวกัน
> 2. **กฎไหนที่ต้องอธิบายให้ผู้ใช้รู้** — ตัวเลขที่ผู้ใช้จะคำนวณเองแล้วได้ไม่เท่าเรา ถ้าไม่บอกไว้ก่อนคือเราผิด
>
> **หน้านี้ไม่ใช่แหล่งความจริง** — ADR คือแหล่งความจริง หน้านี้คือดัชนีที่ชี้กลับไปหา ADR
> ถ้าหน้านี้ขัดกับ ADR → **ADR ชนะ** และหน้านี้คือฝั่งที่ต้องแก้
>
> **ต้องอัปเดตเมื่อไหร่** — ทุกครั้งที่ตัดสินกฎการคำนวณใหม่ระหว่าง grill หรือระหว่างสร้าง ไม่ใช่ตอนจบ Sprint

**คอลัมน์ "บอกผู้ใช้"**
- 🔴 = **ต้องอธิบายบนหน้าจอ** ผู้ใช้จะคิดเองแล้วได้ตัวเลขไม่ตรง
- 🟡 = อธิบายเมื่อถูกถาม / ใส่ใน help
- ⚪ = ภายใน ผู้ใช้ไม่ต้องรู้
- ★ = **ค่าที่ผู้ใช้เป็นคนตั้งเอง และตั้งผิดแล้วตัวเลขเพี้ยน** ต้องมีในคู่มือผู้ใช้ ไม่ใช่แค่บนจอ

## 2. ต้นทุนและ FIFO

| # | กฎ | ที่มา | บอกผู้ใช้ |
|---|---|---|---|
| C1 | ต้นทุนคิดแบบ **FIFO โดยเล่น ledger ซ้ำ (replay)** — **ไม่เก็บต้นทุนไว้ที่ไหนเลย** ไม่มีตาราง layer | ADR 0014 Q2/Q3 | 🟡 |
| C2 | `costPerBaseUnit` = **เงินของ layer หน้าสุด ÷ จำนวนของ layer หน้าสุด** ไม่ใช่ค่าเฉลี่ยทั้งคลัง | ADR 0014 Q3b | 🔴 |
| C3 | **เงินคือสิ่งที่เก็บ ต้นทุนต่อหน่วยคือสิ่งที่คำนวณออกมา** ปัดเศษที่หน้าจอเท่านั้น และส่งข้ามสายเป็น string | ADR 0014 Q12 · Pitfall #20 | ⚪ |
| C4 | **ค่าคงที่ที่ต้องเป็นจริงเสมอ:** มูลค่าคลังรวม = เงินเข้าทั้งหมด − เงินที่ถูกใช้ไป **ตรงถึงสตางค์** | ADR 0014 | 🟡 |
| C5 | ของที่**นับได้เกิน** (recount gain) ตีมูลค่าด้วย **ต้นทุนซื้อครั้งล่าสุด** | ADR 0014 Q5 | 🔴 |
| C6 | ของที่**ขาดจนติดลบ** สร้าง layer ติดลบที่ **ต้นทุนล่าสุดที่รู้** | ADR 0014 Q7 | 🔴 |
| C7 | **การกลับรายการตัด layer ของตัวเอง** ไม่ใช่ตัดหัวคิว | ADR 0014 Q8 | 🟡 |
| C8 | ต้นทุน**วัดแยกรายสาขา** ของชิ้นเดียวกันคนละสาขาเป็นคนละต้นทุนได้ | ADR 0014 Q9 | 🔴 |
| C9 | `occurred_at` ที่เป็นวันที่ล้วน ถูกอ่านว่า **สิ้นสุดของวันนั้นตามเวลากรุงเทพ** | ADR 0014 Q9b | ⚪ |
| C10 | การอ่านต้นทุนทุกครั้ง **บอกเสมอว่าตัวเลขมาจากไหน** (มี fallback ข้อเดียว) | ADR 0014 Q10 | 🔴 |
| C11 | **ข้อยกเว้นข้อเดียวของ C1** — ต้นทุน FIFO ของสาขาต้นทางถูก **แช่แข็งลงบนบรรทัดโอน** พร้อม `cost_source` เพราะถามใหม่ทีหลังจะได้ความมั่นใจของ*วันนี้* ไม่ใช่ของวันที่ส่ง | ADR 0018 Q5 | 🟡 |

## 8. Sprint 4 — POS sales import (ADR 0019 ✅ เขียนแล้ว — กฎในหมวดนี้มีผลจริง)

กฎกลุ่มนี้มาจากการ grill 2026-08-19/20 → **ADR 0019** (Q1–Q17) และถูกสร้างจนครบใน Part 19 (L0–L6)

| # | กฎ | บอกผู้ใช้ |
|---|---|---|
| P1 | **หนึ่งแถว = เมนูหนึ่ง × วันขายหนึ่ง × สาขาหนึ่ง** โดย `bill_id` และเวลาเป็น null ได้ ไฟล์รายบิลกับไฟล์สรุปรายวันลงตารางเดียวกัน | 🟡 |
| P2 | **ทุกแถวต้องมีวันที่ของตัวเอง** ไฟล์ที่รวบทั้งช่วงเหลือเมนูละแถว **ถูกปฏิเสธ** พร้อมเหตุผลภาษาไทย | 🔴 |
| P3 | **หน่วยของการนำเข้าคือ สาขา × วัน** นำเข้าซ้ำ = **แทนที่ทั้งวัน** ไม่ใช่เติมต่อท้าย · ของเก่าเก็บไว้ในสถานะถูกแทนที่ ไม่ลบจริง | 🔴 |
| P4 | **หมวดหมู่มาจาก `menu` ไม่เคยมาจากแถวการขาย** — ไฟล์ที่ไม่มีคอลัมน์หมวด ยังทำกราฟแยกหมวดได้ครบ | ⚪ |
| P5 | **ตัวตนของเมนูคือรหัสจาก POS ไม่ใช่ชื่อ** POS เปลี่ยนชื่อ/เว้นวรรคเกิน ไม่กระทบ | 🟡 |
| P6 | ไม่มีรหัส → ล้างชื่อให้เป็นมาตรฐาน → เทียบตรงตัว → ไม่เจอจึง **เสนอตัวใกล้เคียงด้วย `pg_trgm`** (ใช้ซ้ำจาก ADR 0010) · **ห้ามรวมเมนูเองจากคะแนนความคล้าย** ระบบเสนอ คนตัดสิน ระบบจำ | 🔴 |
| P7 | เมนูที่ไม่รู้จัก → **สร้างเมนูรอตรวจอัตโนมัติ ไม่ปฏิเสธไฟล์** แต่ต้องขึ้นให้เห็นในจอ preview ก่อน commit (Decision #57 · Section D.4) | 🟡 |
| P8 | **รายได้ที่ใช้คิด GP = ยอดหลังหักส่วนลด ไม่รวม VAT ไม่รวม service charge** — VAT เก็บแทนสรรพากร · SC จ่ายออกเป็นค่าแรงตาม Decision #39 ถ้านับเป็นรายได้ GP จะพองเพราะไม่มีต้นทุนขายรองรับ | 🔴 |
| P9 | เก็บดิบครบ 5 ตัว (ยอดก่อนหัก · ส่วนลด · ยอดสุทธิ · SC · VAT) แม้ใช้แค่ตัวเดียวคิด GP — ภพ.30 และ O17 ต้องใช้ | ⚪ |
| P10 | **โปรไฟล์นำเข้าประกาศว่า "ตัวเลขในไฟล์รวม VAT แล้วหรือยัง / รวม SC แล้วหรือยัง"** แล้วแปลงเป็นรูปมาตรฐานตั้งแต่ตอนนำเข้า ห้ามเดา | 🔴 |
| P11 | **บังคับฟิลด์ให้น้อยที่สุด** (วันที่ · เมนู · จำนวน · ยอดสุทธิ · สาขา) ที่เหลือมีก็เก็บ · หน้าจอต้อง**บอกตรง ๆ ว่ามุมไหนดูไม่ได้เพราะไฟล์ไม่มีข้อมูล ไม่ใช่โชว์ 0** | 🔴 |
| P12 | **สาขาไม่ได้มาจากไฟล์** มาจากโปรไฟล์นำเข้าที่ระบบรู้เอง (ระบบเดิมใน AppSheet ให้คนพิมพ์ → พิมพ์ผิดคือยอดทั้งวันไปผิดสาขาเงียบ ๆ) | ⚪ |
| P13 | ไฟล์เป็น **TIS-620** และปีเป็น **พ.ศ.** เป็นเรื่องปกติของ POS ไทย → เป็นข้อบังคับของโปรไฟล์ ไม่ใช่ของแถม | ⚪ |
| P14 | **วันขายมาจาก POS ห้ามคำนวณใหม่จาก timestamp** ถ้าไฟล์บอกวันมาแล้ว — Mise ไม่ใช่เจ้าของความจริงของยอดขาย (Decision #11) ตัวเลขต้องตรงกับจอ POS ไม่งั้นไม่มีใครเชื่อ | 🔴 |
| P15 | ไฟล์ที่ให้มาแต่เวลา → คำนวณวันขายด้วย **เวลาตัดวันต่อสาขา** (ตั้งค่าได้ ค่าเริ่มต้น 05:00) · `business_date` เก็บเป็น **DATE ล้วน** จัดกลุ่มรายวัน/สัปดาห์ใช้ตรง ๆ **ห้าม DATE_TRUNC ทับ timestamp อีกชั้น** (จะลาก Decision #60 กลับมา) | 🟡 |
| P16 | **รายได้ = ราคาที่บันทึกในบิล · delivery apps commission เป็นรายจ่าย ไม่ใช่ตัวหักรายได้** — ค่าคอมถูกหักจากยอดโอนรายเดือน ไม่ได้หักรายบิล จะหักรายบรรทัดก็ต้องเดาทุกบรรทัด และจานเดียวกันจะมีสองรายได้แล้วแต่ช่องทาง | 🔴 |
| P17 | ค่าคอม**ตัวจริง**มาจากใบแจ้งยอดรายเดือน → บันทึกเป็น expense ด้วย Part 16 ที่มีอยู่แล้ว · ผู้ใช้**ไม่ต้องกรอก %** · ถ้าตั้ง % ไว้เพื่อดูตัวประมาณระหว่างเดือน **ตัวประมาณห้ามถูกเขียนเป็นแถวรายจ่าย** (กฎ V4) ไม่งั้นซ้ำกับใบแจ้งยอด และหน้าจอต้องบอกว่าเป็นตัวประมาณ (กฎ C10) | 🔴 |
| P18 | `channel` เป็นฟิลด์ทางเลือก — มีในไฟล์ก็อ่าน ไม่มีก็มาจากโปรไฟล์นำเข้า · ไม่มี channel = แยกไม่ออกว่ากำไรหดเพราะช่องทางไหน | ⚪ |
| P19 | หมวดรายจ่ายตั้งต้นเพิ่ม **`OpEx/Commission/Delivery apps`** — ค่า GP ไม่ใช่ค่าโฆษณา ปล่อยให้แต่ละร้านตั้งชื่อเองจะทำให้ก้อนที่แพงที่สุดก้อนหนึ่งเทียบข้ามร้านไม่ได้ตลอดไป (แตะ seed ของ H.1 → ต้อง migration) | ⚪ |
| P20 | **แถวติดลบและแถวศูนย์ถูกกฎหมายทั้งคู่** (บิลยกเลิก/คืนเงิน · ของแถม/ชิม/โปร) ไม่มี CHECK ห้าม — ปฏิเสธแถวไหนก็ตาม ยอดรวมจะไม่ตรงกับจอ POS ตลอดไป ซึ่งกฎ P14 ห้ามไว้ | 🟡 |
| P21 | **ช่องว่าง / คอลัมน์หาย / แปลงเป็นตัวเลขไม่ได้ → หยุดทั้งไฟล์ ถามผู้ใช้ ห้ามตีความเป็น 0** เพราะที่นี่ทั้ง 0 และค่าติดลบถูกกฎหมาย จึง**ไม่มี `.positive()` ให้พึ่งแม้แต่ตัวเดียว** (บทเรียน Part 18 L2/T14 — `z.coerce.number()` อ่าน null/""/undefined เป็น 0) · เฉพาะ "0" ที่พิมพ์มาจริงในไฟล์เท่านั้นที่แปลว่าศูนย์ | 🔴 |
| P22 | **รายได้ลงสาขาเสมอ ลงแผนกเมื่อเมนูระบุไว้** · ปิดแผนก → ทุกอย่างลง Main ไม่มีคำว่า "ไม่ระบุแผนก" บนจอ (H.1) · เปิดแผนก → เมนูที่ยังไม่ระบุ **แสดงเป็นแถวแยก ห้ามโยนเข้า Main เงียบ ๆ** ไม่งั้นบาร์จะดูกำไรดีเพราะกินรายได้ของครัว · หนึ่งเมนู = หนึ่งแผนก (แยกข้ามแผนกต้องมี recipe) | 🔴 |
| P23 | **หมวดเมนูเป็นตารางของ Mise (`menu_category`) ไม่ใช่ข้อความจาก POS** — ชื่อหมวดใน POS เปลี่ยน กราฟข้ามเดือนต้องไม่ขาด (หลักเดียวกับ P5) · นำเข้าครั้งแรกสร้างหมวดตามที่เจอในไฟล์ให้อัตโนมัติ แล้วโชว์ใน preview (D.4) · ไม่ใช่ตาราง `category` เดิม ซึ่งเป็นผัง COGS/OpEx คนละความหมาย | ⚪ |
| P24 ★ | **เวลาตัดวันอยู่บน `branch` แก้ได้ตลอด** — แต่การแก้มีผลกับ**การนำเข้าครั้งถัดไปเท่านั้น ไม่ย้อนจัดกลุ่มข้อมูลเดิม** เพราะ `business_date` ถูกเก็บเป็น DATE ไปแล้ว (P15) · จะแก้ย้อนหลังต้อง**นำเข้าวันนั้นใหม่** ซึ่งกฎ P3 รองรับอยู่แล้ว | 🔴 ★ |
| P25 ★ | **กำไรขั้นต้น = รายได้ − ต้นทุนของที่ *ขายไป* ไม่ใช่ของที่ *ซื้อเข้ามา*** · วิธีคิดเลือกได้ต่อร้าน (`tenant.gross_profit_method`): **นับสต๊อก** = สต๊อกต้นงวด + ซื้อ − สต๊อกปลายงวด (ใช้ได้เลย ไม่ต้องมีสูตร) · **สูตรอาหาร** = ตัดตามสูตร (รอ Sprint 5) · **ห้ามคำนวณด้วยวิธีหนึ่งแล้วแสดงใต้ชื่ออีกวิธี** ร้านที่เลือกสูตรอาหารเห็น "—" พร้อมเหตุผล | 🔴 ★ |
| P26 | วิธี **นับสต๊อก แม่นเท่าที่การนับสต๊อกแม่น** — ยังไม่มี `CONSUMPTION` (P13/W4) ยอดคงเหลือจึงมีแต่ขึ้นระหว่างรอบนับ ทำให้สต๊อกปลายงวดสูงเกินจริง → ต้นทุนขายต่ำเกินจริง → **กำไรขั้นต้นดูดีเกินจริง** · ทุกแถวต้องแสดงวันที่ปิดนับล่าสุด และแถวที่ไม่เคยนับต้องบอกตรง ๆ | 🔴 |
| P27 | **พัลส์ = ยอดที่ลูกค้าจ่าย** (หลังหักส่วนลด **รวม** VAT และ SC) ซึ่ง**ไม่ใช่**รายได้ตาม P8 · การกระทบยอดเทียบพัลส์กับ `net + vat + service_charge` ของวันนั้น — **เทียบตัวเลขชนิดเดียวกัน** ไม่งั้นจะเตือนทุกวันจนไม่มีใครอ่าน | 🔴 |
| P28 | **พัลส์แก้ได้จนกว่ารายละเอียดของวันนั้นจะถูกบันทึก แล้วล็อก** — หน้าที่มันเปลี่ยนจาก "ตัวเลขที่ใช้ดู" เป็น "หลักฐานที่ใช้ตรวจไฟล์" · ถ้ายังแก้ได้ วิธีที่ง่ายที่สุดในการทำให้คำเตือนหายคือแก้พัลส์ให้ตรงไฟล์ ซึ่งทำลายเหตุผลทั้งหมดที่เก็บมันไว้ | 🔴 |
| P29 ★ | **เตือนเมื่อต่างเกิน 1% หรือ ฿100 แล้วแต่อันไหนมากกว่า · เตือนที่จอ preview ก่อน commit · ไม่บล็อก** (บล็อกแล้วคนจะลบพัลส์ทิ้ง เสียทั้งคำเตือนและหลักฐาน) · **เกณฑ์นี้เดามา** ต้องปรับกับข้อมูลร้านจริงก่อน Beta เหมือนเกณฑ์ความมั่นใจใน Section C | 🔴 ★ |

## 9. Sprint 5 — สูตรอาหารและต้นทุนสูตร (ADR 0021, Part 21)

กฎกลุ่มนี้มาจากการ grill 2026-08-20/21 → **ADR 0021** (Q1–Q18) · R1–R13 มาจาก grill, **R14–R17 ตัดสินตอนสร้าง L3b** · โค้ด: `recipe-graph.ts` · `recipe-guards.ts` · `recipe.ts` · `recipe-cost.ts`

| # | กฎ | บอกผู้ใช้ |
|---|---|---|
| R1 | **ของแปรรูปทำได้สองทาง เลือกหนึ่ง** — "สินค้าแม่หนึ่งตัว + yield" **หรือ** "สูตรผลิต" · **ห้ามมีทั้งคู่** เพราะเป็นวิธีเขียนของสิ่งเดียวกัน ถ้ามีทั้งคู่จะได้ตัวเลขสองชุดที่ขัดกันโดยไม่มีอะไรบอกว่าอันไหนถูก | 🟡 |
| R2 | **สองตัวหาร คนละความหมาย ต้องหารทั้งคู่** — `ต่อ 1 ที่ = ปริมาณในสูตร ÷ จำนวนที่ต่อสูตร` แล้ว `วัตถุดิบดิบ = ต่อ 1 ที่ ÷ (yield_percent/100)` · ตัวแรกแบ่งหม้อเป็นจาน ตัวหลังคิดส่วนที่มีดเอาไป · ภาษาพูดเรียก "yield" ทั้งคู่ | 🔴 |
| R3 | **เปอร์เซ็นต์ yield ของสูตรผลิตคำนวณตอนอ่าน ไม่เก็บ** — เข้า 300 ก. ออก 250 ก. = 83.3% · เก็บไว้เมื่อไหร่จะขัดกับสูตรที่มันมาจาก · **สูตรที่วัตถุดิบคนละมิติ (กรัม + มล. + ฟอง) คิดไม่ได้ → แสดง "—" พร้อมเหตุผล ห้ามเดา** | 🟡 |
| R4 | **ต้นทุนสูตรวัดรายสาขาเสมอ** — สูตรเป็นของทั้งร้าน ต้นทุนไม่ใช่ (สืบจาก C8) · "ต้นทุนกะเพราหมู" มีได้หลายค่าเท่าจำนวนสาขา | 🔴 |
| R5 | **ความมั่นใจของสูตรเท่ากับวัตถุดิบตัวที่แย่ที่สุด ไม่ใช่ค่าเฉลี่ย** — มีตัวไหนที่สาขานี้ไม่เคยซื้อ ทั้งสูตรเป็น LOW และหน้าจอต้องระบุชื่อตัวนั้น · **ห้ามถ่วงน้ำหนักตามสัดส่วนต้นทุน** เพราะของที่ไม่รู้ราคาถูกตีเป็น 0 จึงมีน้ำหนัก 0 → ยิ่งไม่รู้ยิ่งดูไม่สำคัญ ตรรกะกลับหัว | 🔴 |
| R6 | **ต้นทุนสูตรไม่ถูกเก็บที่ไหนเลย** คิดสดทุกครั้งที่อ่าน (สืบจาก C1) · จำผลได้เฉพาะภายใน request เดียว ซึ่งไม่มีอะไรเปลี่ยนได้ · **ไม่มี `recipe_cost_snapshot`** และ "stale" ไม่มีความหมายอีกต่อไป | ⚪ |
| R7 | **สูตรใช้ append + supersede มีวันที่มีผล** — งวดที่คร่อมการเปลี่ยนสูตรต้องคิดจากสูตรที่ถูกต้องของแต่ละวัน ไม่ใช่สูตรวันนี้ทั้งงวด · **สร้างเวอร์ชันใหม่เฉพาะตอนเลขคณิตเปลี่ยน** แก้ชื่อ/หมายเหตุไม่นับ | 🔴 |
| R8 | **วันที่มีผลแสดงเฉพาะตอนที่มันเปลี่ยนคำตอบ** — หน้าประวัติสูตร และงวดที่คร่อมการเปลี่ยน · **ไม่แสดงบนหน้าสูตรปกติ** (กฎ W4 กลับด้าน: อย่าประดับ พูดตอนที่สำคัญ) | 🟡 |
| R9 | **สาขาที่ไม่ได้ผูกสูตรของตัวเอง ใช้สูตรกลางและตามมันไป · สาขาที่คัดลอกไปแล้ว ไม่ตามอะไรอีกเลย** — การกดคัดลอกคือการประกาศว่าสาขานี้ตัดสินใจเอง เพราะการเปลี่ยนสูตรคือการเปลี่ยนวิธีทำงานของครัว ซึ่งเปลี่ยนตามกันทันทีไม่ได้ | 🔴 |
| R10 | **ราคาขายที่ใช้คิด food cost % มาจากยอดขายจริง** (`net_amount ÷ qty`) **ในช่วงเวลาเดียวกับที่คิดต้นทุน** · ไม่มีช่องให้พิมพ์ราคาเอง (หลักเดียวกับ P16) · เมนูที่ไม่มียอดขายในช่วงนั้นแสดง "—" ไม่ใช่ 0% | 🔴 |
| R11 | **ของแปรรูปยังไม่มีสต๊อกจริง — การขายระเบิดทะลุถึงวัตถุดิบดิบเสมอ** · ผลที่ต้องบอกผู้ใช้: **นับสต๊อกของแปรรูปจะเจอ "ของเกิน" ทุกครั้ง** เพราะไม่มีอะไรทำให้ยอดมันขึ้นได้ | 🔴 |
| R12 | **หน่วยในสูตรแปลงตอนอ่าน ไม่เก็บค่าที่แปลงแล้ว** — สูตรคือคำสั่งที่ยืนอยู่ ("ใส่ 1 ถุง") ไม่ใช่บันทึกของอดีตแบบใบสั่งซื้อ (ต่างจาก ADR 0012 Q3 โดยเจตนา) · แก้ `toBaseRatio` ของหน่วยที่มีสูตรอ้างอยู่ **ต้องบอกก่อนว่าจะกระทบสูตรไหน** | 🟡 |
| R13 | **สลับวัตถุดิบข้ามประเภทหรือข้ามหน่วย ต้องล้างช่องปริมาณให้กรอกใหม่** — พริกสด 20 ก. ≠ พริกผัดน้ำมัน 20 ก. · ค่าตั้งต้นที่ผิดคือค่าที่คนกดผ่าน (บทเรียนเดียวกับที่ P21 ปฏิเสธ `parseFloat(x) \|\| 0`) | 🔴 |
| R14 | **แปลง `cost_source` เป็นความมั่นใจ:** `FRONT_LAYER` → HIGH · `DECLARED` → MEDIUM · `LAST_KNOWN` → MEDIUM · `UNPRICED` → LOW · MEDIUM ทั้งสองตัวด้วยเหตุผลเดียวกัน — เป็นตัวเลขจริงของของจริง แต่ไม่ใช่ราคาของที่อยู่ในหม้อ (ตัวหนึ่งคนประมาณ อีกตัวซื้อมาแล้วใช้หมดไปแล้ว) · **MEDIUM ไม่ใช่คำร้องเรียน** ไม่มีอะไรขาด จึงไม่มีอะไรถูกระบุชื่อ (ต่างจาก R5) | 🟡 |
| R15 | **ต้นทุนคิดที่ระดับ "หนึ่งครั้งที่เขียนสูตร" แล้วค่อยหารเป็นต่อที่ ด้วยการหาร*เงิน*** — `ต้นทุนต่อที่ = ต้นทุนทั้งหม้อ ÷ จำนวนที่ต่อสูตร` · เพราะปริมาณ leaf ถูกปัดที่ 3 ตำแหน่ง (Part 22 จะลงบัญชีเลขชุดนี้จริง) การหารก่อนแล้วคูณเงินกลับจะฝังการปัดนั้นไว้ในยอดหม้อ · ผลพลอยได้: **รายการวัตถุดิบบวกกันได้เท่ากับยอดหม้อพอดี** ซึ่งคอลัมน์ที่บวกไม่ลงคือคอลัมน์ที่ไม่มีใครเชื่อ | ⚪ |
| R16 | **เมนูที่เป็นส่วนประกอบแต่ยังไม่มีสูตร = "ไม่รู้" ไม่ใช่ "ฟรี"** — การระเบิดสูตรคืนค่าว่างสำหรับมัน เซ็ทที่มีมันอยู่จึงดูถูกกว่าความจริง · หาไม่เจอจากใบไม้ (ใบไม้เป็น product) จึงต้องกวาดกราฟหาแยกต่างหาก แล้วบังคับทั้งสูตรเป็น LOW พร้อมระบุชื่อ | 🔴 |
| R17 | **สูตรที่ผู้ใช้เปิดอยู่ถูกใช้เป็นรากตรงๆ ส่วนที่อยู่ใต้มันค่อย resolve ตามสาขาและวัน** — ถามว่า "สูตรกลางนี้ถ้าทำที่อโศกจะต้นทุนเท่าไหร่" ต้องได้สูตรกลางที่ราคาอโศก · ถ้า resolve รากด้วย จะกลายเป็นตอบสูตรของอโศกเองที่ราคาอโศก แล้วการเปรียบเทียบข้ามสาขา (R4) จะกลายเป็นการเทียบคนละจาน | 🟡 |
| R18 | **ปริมาณส่งต่อได้เมื่อ "ชนิดเดียวกัน **และ** ของใหม่มีหน่วยชื่อเดียวกัน" เท่านั้น** (ทำให้ R13 เป็นรูปธรรม) — พริกสด→พริกชี้ฟ้า กก.→กก. ส่งต่อได้ · ข้ามไปของแปรรูป หรือของใหม่ไม่มีหน่วยนั้น หรือแทนด้วย**เมนู** → ล้างช่องให้กรอกใหม่เสมอ · ตัดสินที่ server ไม่ใช่ที่ฟอร์ม จะได้ทดสอบได้ | 🔴 |
| R19 | **สลับวัตถุดิบแบบยกชุด เขียน "เวอร์ชันใหม่" ให้ทุกสูตรที่ติ๊ก เหมือนแก้ทีละใบทุกประการ** — ผ่าน `appendVersion` ตัวเดียวกัน · ถ้าแยกทางกันเขียน สองหน้าจอจะให้ประวัติคนละแบบกับการกระทำเดียวกัน · **หมายเหตุของบรรทัดที่ถูกแทนถูกทิ้ง** เพราะมันบรรยายของเดิม ("ซอยละเอียด" ข้างของที่สับมาแล้ว อ่านเป็นคำสั่งทั้งที่ไม่ใช่) | 🟡 |
| R20 | **หน้าเทียบสาขา จัดกลุ่มตาม "สูตร" แล้วนับสาขา ไม่ใช่ไล่ทีละสาขา** (Q9) — ร้านร้อยสาขาที่ทำเหมือนกันหมดยกเว้นสอง ถ้าไล่ทีละสาขาจะได้หน้าจอที่มีบรรทัดเหมือนกันเก้าสิบแปดบรรทัดบังสองบรรทัดที่ต่าง · คำถามจริงคือ "สาขาไหนทำไม่เหมือนชาวบ้าน" ซึ่งเป็นการนับ ไม่ใช่การไล่ | 🟡 |
| R21 | **แต่ละกลุ่มในหน้าเทียบสาขา คิดราคาที่สาขาของกลุ่มนั้นเอง และ*ต้องพิมพ์ชื่อสาขากำกับตัวเลข*** (ต่อยอด R4) — สูตรกลางคิดที่สาขาแรกที่ยัง**ตามสูตรกลางอยู่จริง** · ถ้าทุกสาขาแยกสูตรไปหมด สูตรกลางจะ**ไม่มีราคาให้คิดเลย** แสดง "—" ไม่ใช่ยกสาขาใดสาขาหนึ่งมาสวม · เหตุผล: สองกลุ่มที่ต่างกันแค่ราคาของ จะถูกอ่านว่าเป็นสูตรคนละอย่าง ถ้าไม่บอกว่าเลขไหนคิดที่ไหน | 🔴 |
| R22 | **สูตรที่ถูก supersede ไม่ถูกซ่อน — แสดงในประวัติแบบขีดฆ่า** · มันไม่ได้ครอบคลุมวันไหนเลย (ต่างจากเวอร์ชันที่แค่เก่า ซึ่งยังครอบคลุมวันของมันอยู่ตาม R7) แต่คนที่จำได้ว่าตัวเองพิมพ์มันไป ต้องเห็นว่ามันหายไปไหน | 🟡 |

## 10. Sprint 5 — ตัดสต๊อกตามยอดขาย (ADR 0022, Part 22)

กฎกลุ่มนี้มาจากการ grill 2026-08-24 → **ADR 0022** (Q1–Q11) · N12 เป็นหลักการที่ Kong วางไว้ระหว่าง grill และมีผลเกินขอบเขต Part นี้

| # | กฎ | บอกผู้ใช้ |
|---|---|---|
| N1 | **movement ลงวันที่ตาม "วันขาย" ไม่ใช่วันที่กดปุ่ม** — ไม่งั้นการนำเข้าย้อนหลัง 30 วันจะกองลงวันนี้ทั้งหมด FIFO ตัดชั้นผิดลำดับ และการอ่านต้นทุนย้อนหลัง (`asOf`) จะโกหกทุกวัน | 🟡 |
| N2 | **เมนูหนึ่งจาน ตัดได้ทั้งจานหรือไม่ตัดเลย** — ถ้าอะไรใต้มันระเบิดไม่ครบ (ไม่มีสูตร · ของแปรรูปไม่มี % ผลผลิต · **ส่วนประกอบเป็นเมนูที่ไม่มีสูตร**) ทั้งจานเข้ารายการ "ตัดไม่ได้" พร้อมเหตุผล · คือกฎ R16 ในรูปของสต๊อก — ตัดบางส่วนคือตัวเลขที่ผิดโดยไม่มีอะไรบนจอดูผิด | 🔴 |
| N3 | **coverage วัดเป็น % ของยอดขาย ไม่ใช่ % ของจำนวนจาน** — คำถามจริงคือ "ต้นทุนที่ได้ผิดไปแค่ไหน" น้ำเปล่า 20 บาทกับสเต๊ก 300 บาทไม่ควรนับเท่ากัน | 🔴 ★ |
| N4 | **บิลที่ถูกยกเลิก = ตัวเลือกของร้าน ไม่ใช่ค่าที่ระบบเดา** (`tenant.cancelled_sale_policy`) · ค่าตั้งต้น **"ปรุงไปแล้ว" ตัดเต็ม** — ความผิดพลาดจะโผล่เป็น "ของเกิน" ตอนนับ ซึ่งมองเห็นและสืบสาวกลับได้ · อีกทางโผล่เป็น "ของขาด" ซึ่งหน้าตาเหมือนของหาย | 🔴 ★ |
| N5 | **กดตัดสต๊อกวันเดิมซ้ำ = ยกเลิกทั้งวันแล้วตัดใหม่ ไม่ใช่ตัดเพิ่ม** — กลไกเดียวกับ S6 จึงมีทางเดียวในโค้ด · การตัดเพิ่มจะพลาดสูตรที่ถูก*แก้*ย้อนหลัง เพราะเมนูนั้นนับว่า "ตัดไปแล้ว" | 🔴 |
| N6 | **นำเข้าไฟล์ทับวันที่ตัดสต๊อกไปแล้ว → ยกเลิกอัตโนมัติในทรานแซกชันนำเข้า · ตัดใหม่เป็นขั้นตอนของผู้ใช้** — การยกเลิกไม่ต้องใช้สูตรเลย จึงพังจากปัญหาสูตรไม่ได้ ต่างจากการตัด | 🔴 ★ |
| N7 | **การเคลื่อนไหวชดเชยตีค่าจาก movement เดิม ห้ามคำนวณใหม่** จากสูตรวันนี้หรืออัตราหน่วยวันนี้ (สืบจากกฎของเสีย ADR 0017) · และเกิด **"ตอนนี้"** ไม่ใช่ย้อนไปวันเดิม (สืบจาก ADR 0013 Q6) | ⚪ |
| N8 | **`CONSUMPTION_REVERSAL` คืนชั้นราคาที่มัน*กิน*ไป ไม่ใช่ราคาล่าสุด** — 10 กก. ที่ออกไปที่ 180 ต้องกลับที่ 180 · ถ้าคืนที่ราคาล่าสุด การนำเข้าไฟล์ซ้ำจะเปลี่ยนมูลค่าสต๊อกทั้งที่ไม่มีอะไรเกิดขึ้นจริง (ADR 0014 Q8) · **ข้อยกเว้น:** ยอดสุทธิที่เป็นบวกโดยไม่มี movement ต้นทาง คืนที่ราคาล่าสุดเพราะไม่มีชั้นไหนให้คืน | ⚪ |
| N9 | **ยอดขายที่เก่ากว่าหน้าต่างย้อนหลัง 90 วัน นำเข้าได้แต่ตัดสต๊อกไม่ได้** — เข้ารายงาน coverage เป็นอีกเหตุผลหนึ่ง · `createStockMovementLogic` ไม่ตรวจให้ ผู้เรียกต้องตรวจเอง ไม่งั้น Part นี้จะเป็นตัวเดียวที่มุดกฎที่ทุก Part เคารพ | 🔴 |
| N10 | **กำไรขั้นต้นแบบสูตรอาหาร = มูลค่า FIFO ของ `CONSUMPTION` สุทธิจาก `CONSUMPTION_REVERSAL` ในงวด** · งวดที่ตัดไม่ครบทุกวัน **แสดงตัวเลขพร้อมป้ายความครอบคลุม** ไม่ใช่ซ่อนเป็น "—" (แบบเดียวกับที่ ADR 0019 บังคับเรื่องวันนับสต๊อกครั้งสุดท้าย และ W4) · **ยกเว้นทั้งงวดไม่ได้ตัดเลย = "—"** เพราะ 0.00 อ่านว่าต้นทุนขายเป็นศูนย์ | 🔴 ★ |
| N11 | **สูตรที่มีผลกับวันนั้น ถูกสร้างหลังวันนั้นถูกตัด = สัญญาณให้ตัดใหม่** — ตรวจจับและขึ้นให้เห็น **ไม่ตัดใหม่เอง** เพราะจะเขียนทับงวดที่ร้านอาจปิดบัญชีไปแล้ว · สัญญาณเดียวกันครอบคลุมทั้ง "แก้สูตรย้อนหลัง" (R7) และ "เพิ่งเขียนสูตรเพิ่ม" | 🔴 |
| N12 | **ความกำกวมที่มาจากธรรมชาติของร้าน → เป็นตัวเลือกพร้อมตัวอย่างผลลัพธ์ ไม่ใช่ค่าที่ระบบเดาแทน** · ค่าตั้งต้นติดป้าย "แนะนำ" พร้อมเหตุผล · เห็นสองจังหวะ: หมวด "การคำนวณ" ใน /settings **และ** ตอนที่มันมีผลจริงครั้งแรก · **ไม่ใช่ใบอนุญาตให้ทุกความกำกวมกลายเป็นสวิตช์** — ข้อที่มีคำตอบถูกอยู่แล้วต้องตอบเอง ไม่งั้นหน้าตั้งค่าจะกลายเป็นที่ทิ้งการตัดสินใจ | 🔴 ★ |

## 11. Sprint 5 — Menu Lab และความครอบคลุมของสูตร (ADR 0025, Part 24)

| # | กฎ | ที่มา | บอกผู้ใช้ |
|---|---|---|---|
| M1 | **"ราคาที่ตั้งใจ" ไม่ใช่ "ราคา"** — เป็นราคาที่คิดไว้ตอนออกแบบเมนู เก็บไว้บนฉบับร่าง ไม่ใช่บน `menu` · **พอเมนูมียอดขายแล้ว ราคาที่ขายได้จริงคือราคา** (`net_amount ÷ qty` ตาม P8) ตัวเลขที่ตั้งใจอยู่ข้าง ๆ ไว้เทียบ ไม่เคยแทนที่ | ADR 0025 Q2 · ADR 0021 Q10 | 🔴 |
| M2 | **ต้นทุนใน Menu Lab คิดด้วยเครื่องเดียวกับหน้าสูตร** (recursive + yield-correct + ไม่เก็บ) และ**ต้องมาพร้อมความมั่นใจเสมอ** · ต้นทุนต้องมีสาขา — ค่าตั้งต้นคือสาขาที่มีข้อมูลต้นทุนสดที่สุด และ**ชื่อสาขาอยู่ข้างตัวเลข** ไม่ใช่ในหน้าตั้งค่า | ADR 0025 Q4 · Q6 · ADR 0014 Q9 | 🔴 |
| M3 | **ความครอบคลุมของสูตร = รายได้ของเมนูที่มีสูตร ÷ รายได้ทั้งงวด × 100** (ไม่ใช่นับจำนวนเมนู) · รายการเมนูที่ยังไม่มีสูตร **เรียงตามรายได้** เพราะคำถามคือ "กำไรขั้นต้นที่กำลังเดาอยู่มีเท่าไร" ไม่ใช่ "เหลืออีกกี่เมนู" · คู่กับ N10 ที่พิมพ์กำไรพร้อมความครอบคลุมเสมอ | ADR 0025 Q5 | 🔴 |
| M4 | **ฉบับร่างไม่นับว่ามีสูตร** — ตัดสต๊อกไม่ได้และคิดต้นทุนของวันไม่ได้ · แถวนั้นยังอยู่ในรายการ แต่ติดป้ายว่ามีคนเริ่มทำแล้ว | ADR 0025 Q4 | 🟡 |
| M5 | **งวดที่ไม่มีรายได้เลย = "—" ไม่ใช่ 0%** เพราะ 0% อ่านว่า "ยังไม่มีสูตรสักเมนู" ทั้งที่ความจริงคือ "ยังไม่มีอะไรให้ครอบคลุม" (เหตุผลเดียวกับ N10) | ADR 0025 Q5 | 🟡 |
| M6 | **ชื่อคล้ายกัน = คำใบ้ ไม่ใช่การรวม** — ระบบไม่จัดกลุ่ม ไม่ซ่อน ไม่รวมเมนูให้ (การรวมเมนูคือ Part 25) · แถวที่ไม่ได้ค้นคำใบ้ (เกินโควตา) ต้องไม่ถูกอ่านว่า "ไม่มีตัวซ้ำ" | ADR 0025 Q5 · ADR 0019 Q7 | 🟡 |
| M7 | **"ครอบคลุม" ผูกกับสาขาเมื่อระบุสาขา** — ถามผ่านตัวแก้สูตรตัวเดียวกับที่บัญชีสต๊อกใช้ · ถ้าไม่ระบุสาขา คำถามอ่อนลงโดยตั้งใจ (มีสูตรที่ไหนสักที่ไหม) เพื่อไม่ส่งคนไปเขียนสูตรที่มีอยู่แล้ว | ADR 0025 Q5 · ADR 0021 Q8 | 🟡 |
| M8 | **% ต้นทุนวัตถุดิบ = ต้นทุนต่อจาน ÷ ราคาที่ตั้งใจ × 100** · **กำไรขั้นต้นต่อจาน = ราคาที่ตั้งใจ − ต้นทุนต่อจาน** · ไม่มีราคาที่ตั้งใจ = **"—" ไม่ใช่ 0%** เพราะ 0% คือคำตอบที่สวยที่สุดของคำถามที่ไม่มีใครถาม · ทั้งสองตัวคำนวณ**ที่เซิร์ฟเวอร์** (Decimal ข้ามไป Client Component ไม่ได้) และแสดงคู่กับความมั่นใจเสมอ — 22% บนวัตถุดิบที่ครึ่งหนึ่งยังไม่รู้ราคา ไม่ใช่ 22% | ADR 0025 Q4 · Part 24 L3d/L5b | 🔴 |
| M9 | **เครื่องคิดเลขที่ยังว่าง = ฿0 ที่ความมั่นใจ "ต่ำ"** ไม่ใช่ ฿0 ที่มั่นใจ — หน้าจอที่เพิ่งเปิดไม่มีอะไรบนจอมาค้านตัวเลขที่ดูดี · เป็นข้อยกเว้นเดียวจากกฎ "สูตรต้องมีวัตถุดิบอย่างน้อย 1 รายการ" เพราะไม่มีอะไรถูกบันทึก | ADR 0025 Q3 · Part 24 L3d | 🟡 |
| M10 | **"สาขาที่ข้อมูลต้นทุนสดที่สุด" = สาขาที่มี `PO_RECEIVE` ล่าสุด** เพราะเงินของ FIFO มาจากการซื้อ — สาขาที่มีแต่ของโอนเข้ามาถูกตีราคาด้วยตัวเลขที่ถูกแช่ไว้จากสาขาต้นทาง (ADR 0018) ไม่ใช่ตัวเลขสด · ร้านที่ยังไม่เคยรับของเลย ใช้สาขาแรกตามชื่อ และทุกวัตถุดิบจะขึ้นว่า "ยังไม่รู้ราคา" ซึ่งเป็นความจริงของจานที่ยังไม่มีใครซื้อของให้ | ADR 0025 Q6 · ADR 0014 Q9 | 🟡 |

## 11.5 Sprint 5 — การรวมเมนู (ADR 0026, Part 25) — *สร้างแล้ว ✅ 2026-08-27 (ยกเว้น G5 ที่ยังไม่มีหน้าจอให้ใช้) · G7 เพิ่ม 2026-08-27*

| # | กฎ | ที่มา | บอกผู้ใช้ |
|---|---|---|---|
| G1 | **การรวมเมนูไม่ย้ายยอดขายสักแถว** — เมนูฝั่งแพ้เก็บรหัส POS ของตัวเองไว้ตลอดกาลและ**ยังรับยอดขายใหม่ต่อไปเรื่อย ๆ** เพราะ POS ยังส่งรหัสนั้นมาทุกวัน และรหัสนั้นเรียกคืนไม่ได้ (`menu_pos_identity_unique` ไม่กรอง `deleted_at` โดยตั้งใจ) | ADR 0026 Q1 · ADR 0019 Q7 | 🔴 |
| G2 | **รายงานรวมย้อนหลังเสมอ · การตัดสต๊อกรวมตั้งแต่ `effective_from` เท่านั้น** — รายงานคำนวณสดและย้อนกลับได้ทันที ส่วน movement เขียนลง ledger ที่ append-only การเขียนย้อนอดีตคือการเปลี่ยนสิ่งที่เกิดขึ้นแล้ว · ค่าเริ่มต้น = **วันนี้** | ADR 0026 Q5 · ADR 0011 | 🔴 |
| G3 | **หลังรวม ความครอบคลุมจะมีสองตัวเลขที่ไม่เท่ากัน และทั้งคู่ถูก** — ตัวที่เก็บไว้บน `sales_consumption_run` ตอบว่า *"เดือนนั้นตัดสต๊อกไปได้กี่ %"* (ห้ามขยับตลอดกาล) · ตัวที่คำนวณสดตอบว่า *"ตอนนี้อธิบายเดือนนั้นได้กี่ %"* · **ส่วนต่างคือมูลค่าของการกดโพสต์ใหม่** จึงต้องแสดงคู่กัน ไม่ใช่เกลี่ยให้เท่ากัน | ADR 0026 Q5 · ADR 0022 N10 | 🔴 |
| G4 | **สูตรถูกหาแบบสามชั้น: สูตรของสาขานี้ → สูตรกลางของเมนูนี้ → สูตรของเมนูที่ถูกรวมเข้าไป** — การรวมจึง**เติมได้อย่างเดียว ทับไม่ได้**: เมนูที่มีสูตรของตัวเองอยู่แล้วยังใช้สูตรเดิมทั้งวันในอดีตและอนาคต | ADR 0026 Q2 · ADR 0021 Q8 | 🟡 |

| I4 | **การสร้างร้านใหม่มินต์ uuid ในแอปแล้ว `set_config` ก่อน INSERT แถวแรก** — policy ของ `tenant` ใช้ `USING` เป็น `WITH CHECK` ด้วย จึงต้องมี context ตั้งแต่ก่อนแถวแรกเกิด · **ไม่ใช้ประตูข้าม RLS** เพราะ `/signup` เป็นทางเดียวที่คนยังไม่ล็อกอินเดินถึง | ADR 0030 Q4 | 🟡 |
| I5 | **query ที่ไม่มี tenant context ต้อง error ไม่ใช่คืนศูนย์แถว** — ตัด `true` ออกจาก `current_setting` ทั้ง 47 policy · RLS ที่เงียบทำให้ "ไม่มีข้อมูล" กับ "อ่านไม่ได้" หน้าตาเหมือนกันทั้งหน้าจอ ซึ่งเป็นบาปเดียวกับกฎ A8 แต่ระดับหน้า | ADR 0030 Q5 · A8 | 🔴 |
| I6 | **RLS ไม่ปกป้องตารางที่ไม่มี `tenant_id`** — สี่ตารางของ Auth.js (`app_user` `account` `session` `verification_token`) เปิดอยู่โดยตั้งใจ เพราะตอนล็อกอินยังไม่รู้ว่าเป็นร้านไหน · `app_user` มีเทสต์กันการค้นแบบไม่ผูกเงื่อนไขแทน | ADR 0030 Q6 | 🟡 |
| I7 | **`set_config($1)` ไม่ใช่การต่อสตริง** — บรรทัดที่ตัดสินการแยก tenant ต้องรับ parameter ไม่ใช่ประกอบด้วย template literal | ADR 0030 Context 4 | 🟡 |
| I8 | **ตารางใหม่ที่มี `tenant_id` ต้องมี policy ตั้งแต่ Part ที่สร้างมัน** — เครื่องพิสูจน์ของ I3 ไล่จาก schema เอง จึงแดงทันทีที่ลืม แบบเดียวกับ `sweep-coverage.test.ts` กับ delete order | ADR 0030 Q3 · ADR 0023 | 🟡 |

## 13. รายการที่ต้องอธิบายผู้ใช้ (ดึงจาก 🔴 ข้างบน)

ใช้เป็นตั้งต้นของสองอย่าง: หน้า **"ตัวเลขนี้คำนวณยังไง"** บนจอ (UX pass หลังระบบเสร็จ) และ **คู่มือผู้ใช้ทั้งระบบ** — ข้อที่ติด ★ ต้องอยู่ในคู่มือแน่นอน เพราะเป็นค่าที่ผู้ใช้ตั้งเองแล้วตั้งผิดได้

- **U3** ทำไมวัตถุดิบที่ต้องซื้อ มากกว่าที่สูตรเขียนไว้
- **C2** ทำไมต้นทุนต่อหน่วยไม่เท่ากับราคาที่เพิ่งซื้อมา
- **C5 · C6** ของที่นับเกิน/ขาด ถูกตีราคาด้วยอะไร
- **C8** ทำไมของชิ้นเดียวกันคนละสาขา ต้นทุนไม่เท่ากัน
- **C10** ตัวเลขต้นทุนตัวนี้มาจากไหน
- **V1** ทำไมต้นทุนของแพงกว่าราคาบนใบเสร็จ (ร้านไม่จด VAT)
- **V2** WHT หักจากฐานไหน
- **S1** ทำไม "ยอดที่ควรมี" ไม่เปลี่ยนตามหลังบันทึกแล้ว
- **W1 · W2** ของเสีย ต่างจาก ส่วนต่างจากการนับ ยังไง
- **W4** ทำไมยอดคงเหลือถึงเชื่อได้แค่บางช่วง
- **T1** ทำไมของที่ยังอยู่บนรถ ถึงนับเป็นของปลายทางแล้ว
- **P27 · P28 · P29 ★** พัลส์คือตัวเลขอะไร ทำไมไม่เท่ากับรายได้ ทำไมแก้ไม่ได้แล้ว และเกณฑ์เตือนมาจากไหน
- **P25 ★ · P26** กำไรขั้นต้นคิดยังไง ทำไมสองร้านคิดคนละแบบได้ และทำไมตัวเลขถึงเชื่อได้แค่เท่าที่นับสต๊อก
- **P24 ★** เวลาตัดวันของสาขาคืออะไร ตั้งผิดแล้วเกิดอะไร และทำไมแก้แล้วข้อมูลเก่าไม่ขยับ
- **P22** ทำไมรายได้บางก้อนไม่อยู่ในแผนกไหนเลย
- **P21** ทำไมไฟล์ถูกปฏิเสธทั้งไฟล์เพราะช่องเดียวว่าง
- **P16 · P17** ทำไมรายได้บนจอไม่เท่ากับเงินที่ Grab โอนเข้าบัญชี · เลข "ประมาณ" ต่างจากใบแจ้งยอดยังไง
- **M1** "ราคาที่ตั้งใจ" ต่างจากราคาขายยังไง และทำไมพอขายจริงแล้วราคาขายชนะ
- **M2** ตัวเลขต้นทุนในหน้าออกแบบเมนูมาจากสาขาไหน และเชื่อได้แค่ไหน
- **M3** "ความครอบคลุมของสูตร" คิดจากรายได้ ไม่ใช่จำนวนเมนู
- **M8** % ต้นทุนวัตถุดิบกับกำไรต่อจานคิดจากอะไร และทำไมไม่ใส่ราคาแล้วขึ้น "—" ไม่ใช่ 0%
- **G1** ทำไมรวมเมนูแล้วเมนูเก่ายังอยู่ และยังมียอดขายเข้าทุกวัน
- **G2 · G3** รวมเมนูแล้วรายงานเดือนเก่าเปลี่ยน แต่สต๊อกไม่เปลี่ยน — ทำไมถึงต่างกัน และตัวเลขความครอบคลุมสองตัวหมายถึงอะไร
- **G7** ทำไมลบสูตรนี้แล้วระบบเตือนถึงเมนูอื่น และถ้ายืนยันลบไปแล้วเมนูเหล่านั้นจะเป็นยังไง
- **L1 · L2** "เลิกขาย" ทำอะไรและไม่ทำอะไร · ทำไมเมนูที่เลิกขายแล้วยังมียอดขายเข้า
- **L4** ทำไมเมนูนี้ลบไม่ได้ และทำไม "เลิกขาย" คือคำตอบที่ถูกกว่าเกือบทุกครั้ง
- **P2 · P3 · P8 · P10 · P11 · P14** (Sprint 4) ทำไมไฟล์นี้ถูกปฏิเสธ · อัปทับแล้วเกิดอะไร · "ยอดขาย" ในหน้านี้หมายถึงอะไร
